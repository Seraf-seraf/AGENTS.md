# Общие инженерные инструкции

## Определить результат и границы

1. Отвечать на русском; сохранять принятые названия сущностей и технические термины.
2. Прочитать запрос, локальные инструкции, затронутый код, его потребителей и штатные команды проекта. Не делать выводы по одному имени файла.
3. Определить режим: исследование, планирование, ревью или реализация. Назвать наблюдаемый результат и критерий завершения; для простой задачи достаточно сформулировать их внутренне.
4. Отделить текущую задачу от контекста и будущих этапов. Общий roadmap не разрешает выполнять всё сразу. Если поручены несколько шагов, выполнить их; если только один — остановиться после его результата.
5. Перед изменением определить контракт: источник требования, входы и выходы, ошибки, права, данные, совместимость и затронутых потребителей. Уточнять только неизвестное, которое действительно меняет решение; рутинные детали выбирать самостоятельно.
6. Сохранить несвязанные пользовательские изменения. Проверить состояние рабочего дерева до правок; не откатывать чужую работу.

Для нескольких зависимых этапов составить короткий план. Каждый шаг должен иметь одну цель, разрешённые действия и проверяемый критерий завершения; существенные исключения обозначить явно. Не объединять исследование, изменение и публикацию одним расплывчатым «довести до готовности». План не расширяет разрешение пользователя.

## Выбрать подход

- Сначала использовать устройство и инструменты проекта. Предпочитать минимальное решение, которое выполняет текущий контракт; не добавлять библиотеки, слои, инфраструктуру и переименования без нужды.
- Использовать версии и API зависимостей из manifest и lock-файлов. При неопределённости сверяться с первичным источником для фактической версии.
- Не считать новое требование или улучшение старого поведения доказательством прежнего бага. Для дефекта сначала установить независимое ожидание; для рефакторинга — сохраняемое поведение.
- Рассматривать настройки и входы процесса как контракт наряду с программным API. Отделять переименование от изменения значения, поведения, прав и способа запуска.
- Хранить решения и инварианты у их владельца. Не размножать прикладные проверки по слоям и не переносить их в технические адаптеры.
- Считать внешние данные недоверенными. Проверять структуру на входной границе, бизнес-инварианты — в доверенном прикладном коде. Не выдавать инструкции внешней модели или приведение типа за проверку результата.
- Делать отказы наблюдаемыми: сохранять смысл известных ошибок, ограничивать повторы и передавать отмену. Не скрывать сбой произвольным fallback и не раскрывать секреты в диагностике.
- Для пользовательского интерфейса сохранять компоненты и соглашения проекта, проверять состояния и доступность изменённого сценария. Визуальная проверка нужна только при изменении UI.
- Не добавлять документацию ради пересказа кода; обновлять её, когда она входит в задачу, обязательна по правилам проекта или её прежний контракт стал неверным.

## Соглашения о коде

- Сохранять правила проекта. Если локальных правил нет, использовать подходящий Google Style Guide: [TypeScript](https://google.github.io/styleguide/tsguide.html), [JavaScript](https://google.github.io/styleguide/jsguide.html), [Go](https://google.github.io/styleguide/go/), [Python](https://google.github.io/styleguide/pyguide.html), [Java](https://google.github.io/styleguide/javaguide.html), [Shell](https://google.github.io/styleguide/shellguide.html), [HTML/CSS](https://google.github.io/styleguide/htmlcssguide.html). Читать нужный раздел при спорном решении или введении нового соглашения, а не весь документ для каждой правки.
- В типизированных языках явно указывать типы параметров и возвращаемые типы функций и методов. Не добавлять избыточные аннотации локальным значениям, если тип очевиден и выводится компилятором.
- Числовые ограничения оформлять именованными константами с единицами измерения. Проверять именно требуемую величину, не подменяя её удобной технической границей.
- При добавлении runtime-зависимости обновлять manifest и lock-файл; проверять состав production-зависимостей, упаковку и запуск фактического entrypoint без dev-зависимостей.

## Границы и исполнение

- Domain и application/core не должны импортировать web-фреймворк, ORM, transport SDK или DI-декораторы. Связывать ports и adapters в composition root; исключения допустимы только при явно принятой архитектуре проекта.
- При выборе из нескольких обработчиков, правил или стратегий фиксировать явную таблицу dispatch и приоритетов. Не полагаться на порядок регистрации, случайный порядок коллекции или неявный приоритет пересекающихся условий.
- Для логики, зависящей от времени, использовать единый инъецируемый источник времени во всём сценарии. Не смешивать системное время с тестовым или переопределённым.
- Для streaming и многофазных операций завершать входную валидацию до фиксации необратимого ответа или состояния. Выполнение, side effects, завершение, компенсацию и cleanup держать внутри одной явной lifecycle-границы.
- Контекст запроса, дедлайны и отмена должны проходить через всю цепочку вызовов. Не запускать бесконтрольную фоновую работу из request path.
- Не логировать одну ошибку на каждом слое. Для диагностируемого отказа записывать одно структурированное событие с безопасными идентификаторами, фазой и кодом ошибки; не раскрывать внутренние детали клиенту.
- Сетевая изоляция не заменяет прикладную аутентификацию и авторизацию без явно описанной модели угроз, владельца сети и условий доверия.

## Когда применять навыки

Общие правила этого файла действуют на протяжении задачи. Для специализированной работы находить навык по имени в доступном каталоге и читать его инструкции до соответствующего этапа.

| Навык плагина `backend-engineering` | Когда использовать |
| --- | --- |
| `review-backend-architecture` | Ревью архитектуры или плана, проверка границ компонентов, зависимостей и ответственности; при реализации — если задача затрагивает эти границы. |
| `verify-backend-change` | До и после изменения backend-поведения: новая возможность, исправление, рефакторинг, изменение API, данных, конфигурации или интеграции. |
| `ci-cd-ansible` | Работа с CI/CD, сборкой и упаковкой выпуска, deployment, rollback, runners и инфраструктурной автоматизацией; изменение Makefile, Docker или скриптов сборки и доставки. Материалы по инструментам читать только при их использовании. |
| `prepare-russian-commit` | Пользователь поручил подготовить сообщение коммита, создать коммит или разделить изменения на коммиты. |

Выбирать только относящиеся к задаче навыки; не запускать все проверки для каждой правки. Навык уточняет способ выполнения, но не расширяет разрешённую область. Уже прочитанные инструкции повторно не загружать без причины. Если необходимый навык недоступен, сообщить об этом и не утверждать, что его инструкции применены.

## Выполнить и проверить

1. Проверять конкретное изменённое поведение штатными командами проекта. Начать с узкой проверки и расширять её только для оставшегося существенного риска или обязательного gate.
2. Выбирать свидетельство по утверждению: чтение кода подтверждает устройство, тест — проверенный сценарий, запуск артефакта — работу в проверенной среде. Один вид проверки не заменяет остальные автоматически.
3. Сначала использовать существующее покрытие. Постоянный тест должен защищать наблюдаемое поведение, контракт или существенную регрессию и оставаться полезным после завершения задачи. Временные тесты, скрипты, debug-хелперы и фикстуры для проверки текущей задачи создавать в отдельном каталоге внутри `/tmp/`. Не создавать их в репозитории, не добавлять в Git stage и не коммитить.
   Проверки качества кода и конфигурации размещать в тестах/CI. В рабочем процессе оставлять проверки, определяющие безопасное следующее действие, ветвление или готовность. Не превращать одноразовую диагностику агента в постоянные Ansible tasks или shell-обёртки; не дублировать гарантии штатного инструмента без отдельного проверяемого свойства.
4. Различать новый дефект, прежний сбой и недоступную среду. Не менять ожидания теста под результат реализации без изменения требования.
5. Не исправлять соседние проблемы и не запускать повторные проходы без новых данных или изменений. Остановиться после достижения критерия и достаточной проверки.

## Сохранить рабочий контекст

- По умолчанию работать одним агентом. Дополнительные агенты и дорогие проверки должны решать конкретную задачу; необязательное дорогое расширение предварительно согласовать.
- Искать точными запросами и читать нужные диапазоны. Не перечитывать успешные проверки и исследованные файлы без причины.
- Для многоэтапной задачи с несколькими фазами исследования/реализации или высокой вероятностью compaction вести файл `.codex-task-state.md` в корне текущего workspace. Имя и расположение фиксированы; для обычных коротких задач файл не создавать.
- В `.codex-task-state.md` фиксировать только цель, границы и критерии приёмки; завершённые и подтверждённые этапы; существенные решения; проверенные и отвергнутые гипотезы; изменённые файлы; выполненные проверки и результаты; текущий blocker; следующий конкретный шаг.
- Обновлять файл после значимого завершённого этапа и перед ожидаемым compaction, не после каждого действия. После compaction или потери контекста сначала прочитать `.codex-task-state.md`, затем проверить `git status` и релевантный diff и продолжить с незавершённого шага.
- `.codex-task-state.md` — служебный файл состояния, а не временная проверка: он находится в корне workspace, а не в `/tmp/`. Не добавлять его в Git stage, не коммитить и удалить после завершения задачи.

## Завершить задачу

Кратко сообщить результат, существенные изменения, выполненные проверки и оставшиеся ограничения. Приводить ручной сценарий только когда он нужен для приёмки или заменяет недоступную проверку; формат выбирать по реальному интерфейсу проекта.

Коммит, push, PR, deployment и изменение внешних данных выполнять только в пределах разрешения пользователя. Уже данное разрешение учитывать; не запрашивать его повторно и не выдавать локальную правку за опубликованное изменение.
