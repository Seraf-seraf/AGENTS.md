# Software Engineering

Плагин `software-engineering` для инженерных задач: оценить необходимость и сложность изменения, выбрать достаточное решение, проверить его влияние на потребителей и завершить работу без лишнего расширения. Техническая корректность рассматривается вместе с возможностью выполнить предусмотренный сценарий — через UI, API, CLI или другой сервис. Инструкции и итоговые ответы — на русском.

Общие правила находятся в [AGENTS.md](AGENTS.md): границы задачи, выбор решения, проверки, завершение работы и условия применения навыков. Специализированные навыки подключаются по характеру задачи.

## Навыки

| Навык | Когда применять |

| [Разбор изменения](.agents/skills/analyze-change/SKILL.md) | Оценка необходимости, сложности и рисков; выбор достаточного решения; архитектурное ревью с подтверждёнными замечаниями. |
| [Составление плана](.agents/skills/write-implementation-plan/SKILL.md) | План для исполнительного агента: границы этапов, проверки, точный состав индекса Git и условия остановки. |
| [Проверка изменений](.agents/skills/verify-change/SKILL.md) | Проверка результата потребителя, совместимости, значимых переходов, отказов и возможности продолжить сценарий. |
| [CI/CD и инфраструктура](.agents/skills/ci-cd/SKILL.md) | Сборка, доставка, инфраструктура и восстановление; правила Ansible подключаются только для Ansible. |
| [Подготовка коммита](.agents/skills/prepare-commit/SKILL.md) | Сообщение или создание коммита по запросу: одна причина изменения, понятное описание на русском. |

`AGENTS.md` задаёт общий порядок работы; условия применения специализированных навыков описаны также в их описаниях и таблице выше. Подключать все навыки для каждой правки не требуется. Проектные инструкции определяют фактические инструменты, протоколы, архитектуру и команды проверки.

Проверки выбираются по изменённому контракту, его потребителям и обязательным gates проекта по [CI/CD-навыку](.agents/skills/ci-cd/SKILL.md). Сам факт изменения инфраструктурного файла не требует полного release-цикла. Навык задаёт подготовку стабильного кандидата, диагностику и основания повторов; результаты локальной проверки, реального CI и TEST deploy подтверждаются отдельно в пределах критерия завершения задачи. Имена сред и команды берутся из проекта; внешние действия выполняются в пределах разрешения пользователя. Для правок только документации или текста навыков проверяются содержимое, ссылки и формат поставки.

## Какие проблемы решает плагин

**Технические решения незаметно меняют продукт.** Новое предусловие, общий флаг ошибки или фильтр данных может ограничить предусмотренные действия потребителя. Разбор изменения требует установить источник ограничения, владельца инварианта, затронутые операции и путь восстановления, а не переносить внутренние состояния напрямую в правила интерфейса.

**Корректный отказ превращается в тупик.** Недостаточно безопасно остановить операцию: нужно проверить состояние после остановки и следующий допустимый шаг. Успех, известная ошибка, неопределённый исход и отмена рассматриваются отдельно, когда относятся к изменению. Небезопасные повторы и ослабление авторизации ради удобства не допускаются.

**Объём кода путают с риском, а проверки выполняют ради проверок.** Небольшая правка может затронуть права или данные; большой внутренний рефакторинг может сохранить контракт. Разбор изменения отдельно оценивает сложность реализации, последствия отказа, неизвестность и стоимость подтверждения результата. Дополнительная проверка должна доказывать конкретное существенное свойство.

**Оценка становится источником лишнего функционала или бюрократии.** Необходимость функции и технического механизма связывается с текущим требованием. Согласованный функционал не вырезается из-за сложности, но неподтверждённые усложнения не добавляются «на будущее». Обязательные отчёты, баллы, часы и новые архитектурные слои не вводятся.

## Как выбирается объём работы

`analyze-change` объединяет оценку и архитектурное ревью. Формат результата определяется запросом: оценка, выбранное решение или подтверждённые замечания. Подробные критерии находятся в справочных материалах и читаются по предмету разбора. Навык не зависит от трекера планов, его данных или MCP-инструментов и не создаёт задачи во внешних системах.

Глубина бывает минимальной для понятной локальной правки, целевой для изменённого контракта потребителя и углублённой для существенных рисков, общих ресурсов или сложного восстановления. Выбор обосновывается изменением; низкая сложность не означает низкого риска, а дорогая среда не отменяет обязательный gate.

Планирование и проверка переиспользуют готовые решения и оценку. Самостоятельный план создаётся по запросу; перед ним не нужны обязательные оценочный и архитектурный отчёты. Нужную реализационную деталь планировщик фиксирует в самом плане. Если она не нужна для решения текущего вопроса, отдельный проход не запускается. Наличие UI не означает обязательный UX-аудит; backend-изменение без правок UI всё равно может требовать проверки поведения его потребителя. Анализ не расширяет разрешение пользователя на реализацию или публикацию.

[Калибровочные сценарии](.agents/skills/analyze-change/references/calibration-scenarios.md) помогают проверять решения на разных классах задач. Это критерии для испытаний навыка, а не утверждение, что поведение модели уже проверено во всех клиентах.

## Установка

Источник каталога плагинов: [Seraf-seraf/AGENTS.md](https://github.com/Seraf-seraf/AGENTS.md), ветка `main`.

1. Добавьте репозиторий как marketplace в поддерживающем его клиенте.
2. Установите плагин `software-engineering`.
3. Подключите корневой [AGENTS.md](AGENTS.md) как общие или проектные инструкции в своей рабочей среде. Установка плагина сама по себе не подключает этот файл.

## Структура и упаковка

- `AGENTS.md` — общие инструкции; подключаются отдельно от плагина.
- `.agents/plugin.json` — манифест и версия плагина.
- `.agents/skills/` — навыки и связанные материалы.
- `.agents/plugins/marketplace.json` — каталог установки из репозитория; корень плагина — `.agents/`.

Для переносимого пакета поместите `plugin.json` и каталог `skills/` из `.agents/` в корень ZIP-архива. Каталог marketplace в этот архив не нужен.

Настройки моделей, разрешений и другие настройки клиента задаются в рабочей среде отдельно.

## Обновление

1. Обновите каталог и установленный плагин `software-engineering` средствами своего клиента.
2. Отдельно сравните подключённый `AGENTS.md` с файлом из репозитория и перенесите изменения, сохранив собственные дополнения.

Изменения репозитория не обновляют установленные копии автоматически. Кеш плагина вручную не редактируется.
