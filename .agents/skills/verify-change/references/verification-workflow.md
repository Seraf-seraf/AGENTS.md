# Выбор и выполнение достаточных проверок

## Выполнить и проверить

1. Проверять конкретное изменённое поведение штатными командами проекта. Начать с узкой проверки и расширять её для оставшегося существенного риска или обязательного gate. Для изменения исполняемого CI/CD/IaC выбирать проверки по изменённому контракту и его потребителям по `ci-cd`, сохраняя обязательные gates проекта; сам факт изменения инфраструктурного файла не требует полного release-цикла. Соблюдать порядок подготовки стабильного кандидата и повтора проверок из навыка; локальный результат, реальный CI и TEST deploy подтверждать отдельно в пределах критерия завершения задачи.
2. Выбирать свидетельство по утверждению: чтение кода подтверждает устройство, тест — проверенный сценарий, запуск артефакта — работу в проверенной среде. Один вид проверки не заменяет остальные автоматически.
3. Сначала использовать существующее покрытие. Постоянный тест должен защищать наблюдаемое поведение, контракт или существенную регрессию и оставаться полезным после завершения задачи. Временные тесты, скрипты, debug-хелперы и фикстуры для проверки текущей задачи создавать в отдельном каталоге внутри `/tmp/`. Не создавать их в репозитории, не добавлять в Git stage и не коммитить.
   Проверки качества кода и конфигурации размещать в тестах/CI. В рабочем процессе оставлять проверки, определяющие безопасное следующее действие, ветвление или готовность. Не превращать одноразовую диагностику агента в постоянные Ansible tasks или shell-обёртки; не дублировать гарантии штатного инструмента без отдельного проверяемого свойства.
4. Различать новый дефект, прежний сбой и недоступную среду. Не менять ожидания теста под результат реализации без изменения требования. Успешный повтор не закрывает причину прежнего отказа обязательной проверки; недоступный обязательный этап оставляет проверку незавершённой.
5. Не исправлять соседние проблемы и не запускать повторные проходы без новых данных или изменений. Остановиться после достижения критерия и достаточной проверки.

## Выполнить достаточные проверки

Использовать штатные команды проекта. Запустить относящиеся к изменению тесты и необходимые статические проверки или сборку. Для изменения исполняемого CI/CD/IaC выбирать проверки по изменённому контракту и его потребителям по [CI/CD-навыку](../../ci-cd/SKILL.md), сохраняя обязательные проверки проекта и его порядок подготовки, повторов и подтверждения локальных проверок, CI и развёртывания в тестовом окружении. Форматировать только затронутый код, когда инструмент это поддерживает.

Проверить, что значимые тесты входят в обязательный процесс проверки и исполняются в среде с нужными возможностями. Не терять обязательную проверку и не дублировать набор тестов при изменении их организации; временное исключение должно быть явно согласовано, иметь ответственного, срок и компенсирующую проверку.

Не отключать правило линтера без комментария с технической причиной и областью исключения.

Постоянные тесты должны защищать поведение или контракт. Временные тесты, скрипты, отладочные вспомогательные функции и фикстуры для проверки текущей задачи создавать в отдельном каталоге внутри `/tmp/`. Не создавать их в репозитории, не добавлять в индекс Git и не коммитить.

Различать тесты/CI, эксплуатационные проверки и одноразовую диагностику. В рабочем коде и инфраструктуре оставлять проверку, когда она определяет безопасное действие, ветвление или готовность. Не превращать проверку гипотезы агента в постоянную задачу Ansible, обёртку командной оболочки или предварительную проверку. Сначала учесть гарантии штатного инструмента; дополнительная проверка должна обнаруживать иной существенный отказ. Для инфраструктурной части использовать [CI/CD-навык](../../ci-cd/SKILL.md) в пределах изменения.
