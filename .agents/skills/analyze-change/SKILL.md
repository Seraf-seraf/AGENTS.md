# Разбор изменения

Соблюдать действующие общие и проектные инструкции. Работать в запрошенной области по актуальным требованиям, коду, потребителям и проверкам. Анализ сам по себе не разрешает реализацию, добавление в индекс, коммит, публикацию или изменение внешних данных. Не управлять работой через трекер и не вызывать его MCP-инструменты.

## Определить требуемый результат

1. Различать оценку необходимости, сложности и рисков, выбор проектного решения и ревью существующего кода, решения или плана. Эти результаты не образуют обязательную последовательность. Если поручены несколько, выполнить их в данном объёме, переиспользуя общие факты и решения.
2. Отделять требуемый наблюдаемый результат от предложенного способа и текущего ограничения реализации. Учитывать принятые границы, владельцев данных и политик, явные исключения и источник каждого применяемого правила.
3. Для оценки использовать доступные сведения; отсутствие кода обозначать как ограничение точности, не восполнять выдуманными деталями. Для подтверждённого замечания нужны требования и проверяемое основание: нехватка сведений не доказывает дефект.
4. Узкий вопрос по уже известному коду или выводу не превращать в полный разбор. Готовое исследование переиспользовать; повторно изучать затронутые предпосылки при новых данных, изменении области или зависимостей.

## Читать критерии по предмету разбора

| Предмет | Обязательные относящиеся правила |
| --- | --- |
| Необходимость, сложность, риск, неизвестные или стоимость проверок | [Оценка изменения](references/assessment.md). |
| Выбор границ, ответственности, существующего сервиса или новой абстракции | В [архитектурных критериях](references/architecture.md) — границы и достаточный уровень изменения. Готовое принятое решение не выбирать заново без новых оснований. |
| Ревью кода, решения, рефакторинга или готового плана | [Архитектурные критерии](references/architecture.md), включая подтверждение каждого замечания. При неясной необходимости механизма, выборе между решениями или существенном изменении контрактов применять критерии оценки; готовую оценку переиспользовать без отдельного отчёта и повторного прохода. |

Выбирать применимые разделы, не выполнять весь справочник как новый рабочий процесс. Общие факты устанавливать один раз и использовать в выбранных критериях. При проектировании не объявлять ещё не написанный код существующим дефектом и не искать обязательное количество замечаний.

## Представить результат и завершить

- Для оценки вернуть необходимый результат, минимальное решение, сложность с основаниями, риски, неизвестные и достаточные проверки с их стоимостью по правилам оценки. Для простой задачи достаточно нескольких предложений.
- Для проектирования зафиксировать выбранные контракты, ответственность и существенные компромиссы в объёме запроса. Альтернативы и миграцию разрабатывать, когда они поручены; не превращать ревью в перепроектирование.
- Для ревью вернуть подтверждённые ошибки с доказательствами и минимальными исправлениями по архитектурным критериям. Если запрошены только ошибки, не подменять их рисками или предпочтениями. Отсутствие замечаний допустимо.

Не создавать отдельные оценочный, архитектурный и плановый отчёты, если эти результаты не поручены. План реализации составляет [навык планирования](../write-implementation-plan/SKILL.md) только по соответствующему запросу. Для проверки реализации использовать [проверку изменений](../verify-change/SKILL.md), для доставки — [CI/CD](../ci-cd/SKILL.md) в границах задачи. Ссылки не предписывают запускать все навыки.

Завершить после достаточной проверки запрошенной области и относящихся исправлений. Не повторять опровергнутое замечание и не запускать новый аудит без изменения кода, предпосылок или новых данных. Указать существенные ограничения результата; непроверенная граница не является доказанной корректностью или дефектом.

[Калибровочные сценарии](references/calibration-scenarios.md) читать при изменении самого навыка или спорном выборе глубины, а не для каждой задачи. Они задают примеры ожидаемых решений, не универсальную классификацию проектов и не подтверждение работы модели.
