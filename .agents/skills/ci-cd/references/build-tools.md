# Makefile, Docker, командная оболочка и локальная проверка CI

Применять разделы для инструментов, участвующих в изменённом пути исполнения. Общий порядок обязательных проверок брать из основного навыка.

## Совместимость и подготовка

- Для новой возможности инструмента проверить поддержку у всех исполнителей соответствующей конфигурации: локально, на исполнителе CI и целевом хосте. Получить фактическую версию той команды, которая запускается под рабочим пользователем; наличие бинарника само по себе не подтверждает совместимость. Нужную версию обеспечивать существующим механизмом подготовки среды.
- Собственный разбор машинного вывода проверять на корректных результатах используемых версий инструмента и на отрицательных сценариях. Учесть значения по умолчанию, пропущенные поля и нормализацию по документированному контракту. Если преобразование теряет нужное свойство, проверять его по сохраняющему это свойство представлению; не ослаблять отклонение действительно неверного ввода.
- Новый или сокращённый режим подготовки выполнить с чистой рабочей копии, без ранее созданных каталогов времени выполнения, томов и маркеров готовности. Затем запустить его непосредственного потребителя без предварительной полной начальной подготовки. Проверить повторное применение отдельно: работа в подготовленной среде доказывает только повторный путь. Изолировать очистку от рабочих данных пользователя.
- До дорогого прогона доступ к нужным ресурсам, включая пути, доступные для записи, подтвердить минимальной операцией из процесса-потребителя с его фактическими UID/GID, дополнительными группами, монтированиями и окружением. Это требуется и при подключении нового ресурса с прежним пользователем; проверка из командной оболочки хоста или от имени root не подтверждает доступ приложения. Подготовленные каталоги и файлы должны оставаться доступны пользователю последующего процесса.

## Локальная проверка конвейера CI

- Для GitHub Actions использовать принятую проектом семантическую проверку рабочего процесса CI; при её отсутствии — [actionlint](https://github.com/rhysd/actionlint). Проверять выражения, входы/выходы и зависимости заданий CI; средство разбора YAML подтверждает только синтаксис YAML.
- Для GitLab применять штатные проверки и [CI Lint](https://docs.gitlab.com/ci/yaml/lint/) с подключаемыми файлами и контекстом проекта. CLI/API обращаются к GitLab: это сетевая проверка, а симуляция создания конвейера CI не исполняет его задания. Изменённые подключаемые файлы должны входить в проверяемую конфигурацию; ссылка на прежнюю версию файла не проверяет локальные изменения. Недоступную серверную проверку обозначить отдельно.
- При изменении пользователя, конфигурации или скрипта найти все точки вызова затронутого контракта, включая неизменённые рабочие процессы CI. Локально воспроизводить команду CI целиком: обёртки `sudo`/`env`, фактические UID/GID и группы, `HOME`, рабочий каталог, существенное окружение, инструменты и зависимости. Прямой запуск скрипта не подтверждает вызов через другую обёртку. Сначала искать существующий Makefile, скрипт или иную штатную точку входа; не создавать второй набор команд специально для локального прогона. Невоспроизведённые условия CI обозначить отдельно.
- Использовать локальный эмулятор конвейера CI, если он принят в проекте, с учётом его ограничений. Например, [act](https://nektosact.com/not_supported.html) не подтверждает поведение прав, управления параллельными запусками и секретов окружений. Успех эмулятора не закрывает эти проверки в реальной CI-системе.

## Makefile

- Существующий Makefile использовать как основной интерфейс типовых операций. Сначала искать готовую цель; новую добавлять только для повторяемого сценария.
- Цели без файлового результата объявлять `.PHONY`.
- Не прятать в цели необратимые операции и изменения окружения пользователя: назначение должно быть явно видно из имени, а выполнение — разрешено задачей.

## Docker

- При создании или изменении сборки образа предпочитать многоэтапную сборку, небольшой образ для запуска, непривилегированного пользователя, `.dockerignore` и явно зафиксированные версии базовых образов. Изменение связей компонентов в Compose не требует попутной перестройки Dockerfile.
- Не помещать секреты в образ, Dockerfile, аргументы сборки или репозиторий. Конфигурацию передавать во время запуска.
- При изменении образа проверять точный `CMD` и точку входа, зависимости рабочей среды, минимальный запуск и затронутое поведение проверки работоспособности. При подключении готового образа проверять его интеграцию через существующий Compose и конфигурацию времени выполнения; не компилировать заново согласованную готовую поставку.
- Для Compose учитывать, что [`config`](https://docs.docker.com/reference/cli/docker/compose/config/) объединяет источники, подставляет переменные и нормализует модель. Выбирать представление для проверяемого свойства; вывод с подставленными секретами не печатать и не сохранять в артефакты.

## Скрипты командной оболочки сборки и доставки

- Использовать командную оболочку, заявленную средой и проектом. Для POSIX `sh` сохранять совместимый синтаксис и `set -eu`; не навязывать POSIX другим языкам или средам выполнения.
- Заключать подстановки переменных в кавычки; обязательные входы проверять до мутаций, для обязательных непустых переменных использовать `${VAR:?}`. Ожидаемые ненулевые коды обрабатывать явно.
- Передавать внешние входы через аргументы или документированные переменные окружения; не полагаться на случайные локальные значения.
- Выполнить `shellcheck` для изменённых скриптов с учётом их диалекта и, когда применимо, безопасный запуск с минимальными тестовыми входными данными. Если инструмент недоступен, сообщить это ограничение.
- Исключение правила линтера сопровождать комментарием с технической причиной и областью действия.
