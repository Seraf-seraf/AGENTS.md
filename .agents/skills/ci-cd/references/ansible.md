# Ansible: условные правила исполнения

Применять только к Ansible-части задачи. Общий контракт доставки и критерии проверки брать из основного навыка.

## Структура и состояние

- Следовать существующей структуре. Роль выделять для целостной инфраструктурной ответственности, которую нужно отдельно сопровождать или переиспользовать. Небольшая задача допустима прямо в сценарии Ansible; отдельная роль на каждую фазу или несколько строк не нужна.
- Описывать желаемое состояние штатными модулями `user`, `file`, `package`, `copy`, `template`, `systemd_service` и подходящими модулями коллекций. Не писать собственную последовательность обнаружения и исправления состояния, которое уже обеспечивает модуль.
- Значения роли по умолчанию хранить в `defaults`, различия окружений — в описании узлов и групп Ansible; секреты получать из защищённого источника. Константы держать внутри реализации, производные пути вычислять из одного корня. `extra_vars` оставлять для реальных входов запуска; не дублировать ими всё описание узлов и групп Ansible.
- Не превращать каждый литерал в параметр с последующим `assert`, требующим прежнее фиксированное значение. Сохранять существующие внешние параметры до отдельно разрешённого изменения их контракта.
- Для конфигурации использовать `copy` или `template`, при наличии штатного валидатора — `validate`; перезапускать или перечитывать конфигурацию обработчиком только при изменении. Формат прикладного конфига и операции над прикладными данными остаются у сервиса.

## Проверки внутри сценария Ansible

- Оставлять проверку, если её результат нужен для безопасного действия, выбора ветки или подтверждения готовности: обязательный внешний вход, опасная цель удаления, чужой ресурс, работоспособность сервиса. Не добавлять проверки только для подтверждения того, что агент правильно написал задачи.
- Доверять результату штатного модуля в пределах его контракта. Не окружать каждую установку цепочкой `stat → assert → действие → stat → assert`; отсутствие каталога, который сценарий Ansible должен создать, само по себе не ошибка.
- Дополнительную проверку обосновывать иной границей или свойством, которое модуль не обеспечивает. Например, корректный синтаксис nginx-конфига не доказывает доступность приложения через внешнюю точку входа.
- Когда файловая проверка нужна, явно выбирать тип объекта и `follow`: ссылка или её цель. Не заменять проверку опасной цели предположением о наличии пути.
- Проверки качества инфраструктурного кода выполнять в тестах/CI, временную диагностику — в `/tmp/`. Не переносить тот же набор самопроверок в постоянный скрипт командной оболочки.

## Пользователи выполнения и предварительные условия

При изменении пользователя выполнения или транспорта проследить `ansible_user`, `become_user` и владельцев файлов/процессов. Подтвердить передачу и выполнение безопасного модуля под затронутой парой пользователей: SSH и NOPASSWD не доказывают доступ к временным файлам модуля. При переключении между непривилегированными пользователями проверить выбранный механизм доступа, например POSIX ACL.

При подключении нового ресурса подтвердить доступ операцией из процесса-потребителя, даже если пользователь выполнения не менялся. Проверка с управляющего узла или от имени root не подтверждает доступ приложения. Различать версии инструментов на управляющем узле и управляемом хосте; нужную версию обеспечить существующим путём начальной подготовки среды и проверить команду под пользователем, который её использует.

Предварительные условия транспорта и повышения привилегий (`become`) устанавливать через уже работающий путь начальной подготовки среды до первой зависимой задачи. Не расширять весь сценарий Ansible до прав root ради одной операции. Эти проверки среды не требуют постоянного сценария Ansible для проверки пользователя выполнения и предварительных условий, если он не нужен эксплуатации.

Синтаксическая проверка с тестовым описанием узлов и групп Ansible подтверждает код сценария. Доступность обязательных входов в целевом описании узлов и групп Ansible и их передачу сервису проверить отдельно до первой попытки выпуска, не раскрывая секретов. Использовать существующий валидатор владельца конфигурации.

## Задачи и проверка

- Использовать полные имена модулей. Для модуля `command` предпочитать `argv`; модуль `shell` выбирать только при необходимости возможностей командной оболочки.
- Задавать `changed_when` и `failed_when`, когда стандартный результат не отражает нужную семантику. Не повторять стандартный отказ по ненулевому коду и не скрывать изменения через безусловный `changed_when: false`. Не использовать `ignore_errors` для сокрытия отказа; допустимые исходы обрабатывать явно.
- Давать сценариям, задачам и обработчикам Ansible содержательные русские имена; `register` и фактам — имена с областью ответственности; режимы доступа задавать строками. Не создавать `set_fact` только ради переименования уже доступного значения.
- Для операций с секретами использовать `no_log`; наружу выводить только безопасную диагностику.
- Запустить обязательные проверки проекта для затронутых файлов. `ansible-lint` уже выполняет проверку синтаксиса сценариев Ansible; отдельный `ansible-playbook --syntax-check` нужен, если сценарий Ansible не покрыт или требуется другое описание узлов и групп либо другой контекст. Отдельное средство разбора YAML нужно для непокрытых файлов, а не автоматически как ещё одна обязательная проверка.
- При изменении поведения Ansible-пути подготовки или выпуска применить штатный сценарий Ansible в изолированной представительной среде, проверить функциональный результат, затем повторить применение: без неожиданных изменений и лишних рестартов. Для нового или сокращённого пути подготовки проверить чистое состояние без предварительной полной начальной подготовки. Объём и порядок остальных проверок определять по изменённому контракту и обязательным проверкам из основного навыка. `--check` помогает, но не доказывает реальное применение и идемпотентность. Использовать существующую тестовую среду; Molecule добавлять при потребности в сопровождаемых сценариях, а не ради каждой локальной правки. Недоступные проверки указать явно.

## Основания

- [Стратегии тестирования Ansible](https://docs.ansible.com/projects/ansible/latest/reference_appendices/test_strategies.html): модули обеспечивают заявленное состояние, функциональные проверки подтверждают работу приложения; использовать один путь развёртывания в средах разработки и предварительной проверки выпуска.
- [Jeff Geerling: тестирование ролей Ansible с Molecule](https://www.jeffgeerling.com/blog/2018/testing-your-ansible-roles-molecule/): локально воспроизводить применение роли, повторное применение и проверку результата. Публикация описывает принцип; актуальные команды и конфигурацию брать из [документации установленной версии Molecule](https://docs.ansible.com/projects/molecule/workflow/).
