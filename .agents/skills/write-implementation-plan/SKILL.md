# Составление плана реализации

Соблюдать действующие общие и проектные инструкции. Результат — однозначный MD-план с принятыми проектными решениями; исполнитель не должен заново проектировать задачу. Подготовка плана не запускает реализацию, staging или коммиты описанной задачи.

## Использовать профильные правила

Этот навык владеет составлением плана и его структурой. Применять профильные правила только к относящимся частям задачи, переиспользовать готовые выводы и переносить в план конкретные решения вместо копирования общих чек-листов.

| Владелец | Что использовать при планировании |
| --- | --- |
| [assess-backend-change](../assess-backend-change/SKILL.md) | Достаточность решения, сложность, риски, неизвестные и стоимость проверок, когда требуется такая оценка. |
| [review-backend-architecture](../review-backend-architecture/SKILL.md) | Границы и ответственность, выбор существующего контракта или новой абстракции; проверку предлагаемой архитектуры. |
| [verify-backend-change](../verify-backend-change/SKILL.md) | Сценарии и глубину подтверждения, red/green для изменения поведения и сохранение поведения при рефакторинге. |
| [ci-cd-ansible](../ci-cd-ansible/SKILL.md) | Проверки и условия исполнения затронутой сборки, доставки и инфраструктуры. |
| [prepare-russian-commit](../prepare-russian-commit/SKILL.md) | Состав и сообщение коммита, когда пользователь поручил коммиты. |

Не создавать собственную методику оценки, архитектурный стандарт, полный тестовый регламент или протокол трекера. Учёт выполняется по отдельным действующим инструкциям и не определяет техническую структуру плана.

## Подготовить содержание

1. Прочитать запрос, относящиеся актуальные исходники, спецификацию, согласованные решения, переданные результаты исследования и штатные команды. Готовое исследование переиспользовать; проверку применимости выводов по коду не превращать в повторный аудит.
2. Разрешить существенные проектные вопросы до передачи исполнителю. Зафиксировать интерфейсы, поведение, ошибки и зависимости в объёме задачи. Для неоднозначного правила привести минимальные примеры «состояние → действие → ожидаемый результат», пригодные для приёмки.
3. Включать исследование в план, только если пользователь поручил его. Указать предмет, источники или эксперимент, способ проверки, ожидаемый вывод и условие завершения; зависимую реализацию описывать после подтверждения нужного решения. Если непредвиденная существенная неизвестность мешает составить исполнимую часть, сообщить её и уточнить недостающее; не выдумывать API, команды или продуктовые требования.
4. Разделить работу на этапы с одним законченным, самостоятельно проверяемым результатом. Внутри этапа возможны несколько TDD-шагов; RED и GREEN не делать обязательными границами коммитов. Для небольшой задачи достаточно одного этапа.

## Соблюсти единую схему MD-плана

Использовать разделы в указанном порядке. Подробность определять в одном месте; в остальных давать короткую ссылку, не переписывать ту же инструкцию.

1. **Контекст и описание задачи.** Проблема, текущее поведение и требуемый наблюдаемый результат. Пометить как справочную часть, не команду реализовать всё описанное.
2. **Решения, границы и правила исполнения.** Требования, принятые решения, область и исключения; правила из следующего раздела. Не вводить обязательные поля репозитория, ветки или исходного commit SHA: совместимость определяется нужными контрактами текущего проекта.
3. **Карта этапов.** Стабильные ID, цели и зависимости по результатам. Для независимых этапов отметить допустимую параллельность; при пересечении указать общие файлы и владельца сведения изменений. Этап с ещё не готовым нужным контрактом не считать независимым.
4. **Исполняемые этапы.** Каждый этап заполнить по таблице ниже. Неприменимое поле кратко объяснить, не выдумывать работу ради шаблона.
5. **Общая приёмка и сводный список файлов.** Результат всей задачи и необходимые общие проверки; объединение изменяемых файлов этапов (CREATE/MODIFY/DELETE) с указанием их ID. Сводку выводить из этапов, не поддерживать вторым независимым staged-манифестом. Различать проверку одного этапа и финальную проверку задачи.

| Поле этапа | Обязательное содержание |
| --- | --- |
| **ID и цель** | Одно конкретное изменение или результат исследования. |
| **Начало** | Проверяемые предусловия: результаты зависимых этапов, существующие интерфейсы, данные или доступная среда. Не привязывать старт к неизменности всего HEAD. |
| **Разрешённые изменения** | Точные пути относительно проекта и символы; для каждого USE, CREATE, MODIFY или DELETE и конкретное действие. USE — существующий компонент для использования, в stage не входит. |
| **Действия** | Последовательность реализации выбранного решения либо порученного исследования. Значимые контракты зафиксировать; рутинные локальные детали оставить исполнителю. |
| **Проверки** | Сценарии из требований, фактические команды и рабочая директория, ожидаемый результат и нужная среда. Описать применимый TDD-цикл по verify-backend-change; не требовать искусственного RED для чистого рефакторинга, документации или исследования. |
| **Stage** | Точный список добавлений, изменений и удалений этапа и команды git add с конкретными путями. Для общего файла обозначить hunks этапа; allowlist путей сам по себе не исключает чужое содержимое. Указать ожидаемый staged diff перед фиксацией. |
| **Фиксация** | По умолчанию предусмотреть один локальный коммит законченного этапа по prepare-russian-commit. Явно указать режим: stage + commit при уже данном поручении коммитов, иначе stage. План сам не выдаёт такого разрешения. |
| **Конец** | Конкретное конечное состояние, результаты обязательных проверок и соответствующий режиму результат stage/commit. Короткая передача: что достигнуто, что проверено, существенные ограничения и оставшаяся работа. |
| **STOP** | Завершить работу после результата назначенного этапа. Назвать существенные несоответствия, при которых зависимую работу остановить и сообщить препятствие. Будущую работу помечать как контекст передачи. |

## Включить правила ограниченного исполнения

Поместить в раздел правил самого плана, чтобы они были доступны исполнителю без этого навыка:

- По умолчанию один запуск выполнения охватывает один назначенный этап. Несколько этапов выполнять, если пользователь явно поручил этот объём; после последнего остановиться. Общее описание и последующие этапы не разрешают начинать их. При неясном назначении этапа уточнить его до изменений.
- Внутренние шаги назначенного этапа последовательно выполнить до его конца; не требовать нового подтверждения между RED и GREEN. Проверки этапа не должны требовать ещё не порученной реализации будущих этапов.
- Разрешать адаптацию локальных деталей без изменения согласованных контрактов и ответственности. Изменение бизнес-правила, публичного контракта, модели данных, зависимостей или области требует пересмотра относящейся части плана. Несвязанные параллельные изменения или новый HEAD сами по себе не блокируют работу; сверять затронутые предпосылки.
- Для повтора и продолжения сопоставить фактическое состояние с началом и концом назначенного этапа. Готовое проверить без дублирования; частично выполненное продолжить с недостающего действия. Сохранять зафиксированные пути, имена миграций и контрактов; не генерировать новый комплект при каждом запуске. При отсутствии относящегося diff не создавать пустой или повторный коммит.
- При параллельной записи использовать отдельные рабочие копии либо одного назначенного владельца общего индекса и коммитов. Совпадение имени файла не разрешает включить чужие hunks. Stage добавлять точными путями; для смешанных файлов — только hunks этапа, без git add . или git add -A. При режиме stage без коммитов явно учитывать накопленные изменения своих этапов и не очищать чужой индекс.
- Готовый коммит этапа включает относящиеся код, постоянные тесты и необходимые контракты вместе; следует после проверок. Коммит не разрешает следующий этап, push, PR или deployment. Уже данное пользователем разрешение учитывать без повторного запроса.

## Проверить и выдать план

Провести цикл ревью и исправления до выдачи: проследить требования до этапов и приёмки, согласованность зависимостей и конечных состояний, исполнимость команд и целостность stage. Устранить дублирование существующего кода командами создания, пересечения без владельца, ссылки на будущий отсутствующий код и конкурирующие определения одной подробности. Архитектуру и выбранные проверки оценивать по их владельцам выше.

После исправлений повторять проверку затронутых частей до устранения найденных противоречий. Неразрешённый существенный вопрос обозначать явно, не выдавать зависимый этап как готовый. Не включать в план историю собственного ревью и не утверждать, что проверки будущей реализации уже выполнены.

Сохранить итог в MD с ASCII-именем в согласованном месте. Для возобновления использовать существующий механизм рабочего состояния проекта, не заводить обязательный второй журнал. При изменении или испытании этого навыка использовать [калибровочные сценарии](references/calibration-scenarios.md), не запускать их при составлении каждого плана.
