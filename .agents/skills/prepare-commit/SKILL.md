# Подготовка коммита

Учитывать действующие общие и проектные инструкции при их наличии. Навык не требует отдельного файла общих инструкций.

## Определить, нужен ли коммит

- Если пользователь попросил только сообщение, подготовить текст. Сохранить индекс и историю.
- Если поручено создать коммит, включить только разрешённые изменения. Поручение включает необходимую подготовку индекса.
- Если поручено отправить конкретные изменения, которых ещё нет в коммитах, создать необходимые коммиты этих изменений. Если поручено отправить готовые коммиты, оставить индекс и рабочее дерево без изменений. Для команд чтения, которые могут обновить индекс, отключить необязательные блокировки.
- Если для порученной отправки нужен коммит, а пользователь запретил коммит или запись в индекс, выполнить независимую работу. Уточнить разрешение до записи в индекс, коммита и отправки.

## Изучить изменения

1. Проверить `git status`, изменения, добавленные и не добавленные в индекс Git.
2. Определить логическую причину и изменение контракта, а не перечислять файлы или повторять формулировку задачи.
3. Сопоставить реализацию, тесты, схему, конфигурацию, сгенерированные артефакты и документацию, относящиеся к одному поведению.
4. Отделить пользовательские и несвязанные изменения, включая уже добавленные в индекс Git. Не добавлять чужие изменения, не включать их в свои коммиты и не откатывать.
5. Перед коммитом проверить, какие относящиеся проверки выполнены. Если часть проверок не выполнена, явно сообщить об этом.

Для изменения исполняемого CI/CD/IaC до коммита выполнить локальные проверки, выбранные по изменённому контракту и его потребителям по [CI/CD-навыку](../ci-cd/SKILL.md), сохраняя обязательные проверки проекта и порядок подготовки стабильного кандидата. Сообщение об ограничении не заменяет прохождение проверки или согласованное исключение. Успешную локальную проверку отличать от последующих подтверждений реального CI и тестового развёртывания; разрешение на коммит само по себе не разрешает отправку изменений в удалённый репозиторий или развёртывание.

## Определить границы коммита

- Один коммит должен иметь одну семантическую причину изменения, которую можно закончить фразой «чтобы …» без союза между независимыми целями.
- Реализацию и регрессионный тест одного поведения держать вместе.
- Разделять независимые исправления, переименования в API и конфигурации, изменения топологии и безопасности, зависимостей и сборки, форматирование и очистку кода.
- Не маскировать изменение поведения типом `refactor`. `refactor` допустим, только если неизменны наблюдаемый результат, ошибки, данные, API, контракт конфигурации и смысл правил безопасности.
- Если изменение одновременно исправляет дефект и перестраивает код, сначала выделить минимальное исправление поведения с тестом, затем отдельный рефакторинг с сохранением поведения, если история от этого становится понятнее.
- Перед добавлением в индекс Git перечислить точные файлы или фрагменты изменений каждого будущего коммита. Если файл содержит несколько причин или чужие изменения, разделить фрагменты; совпадение пути не означает принадлежность всего файла к одному коммиту.
- Количество коммитов определяется независимыми семантическими причинами, а не количеством файлов или формой запроса «создай коммит». Один коммит допустим для одной причины. Если пользователь явно требует ровно один коммит, а причин несколько, обозначить конфликт до фиксации и не объединять независимые изменения без согласования.

## Сформировать сообщение

Использовать формат:

```text
type(scope): краткое действие на русском
```

- Выбирать из `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`, `chore`, `perf`.
- Указывать область изменения (`scope`), только когда она уточняет, к чему относится коммит.
- Заголовок, состоящий только из типа — `fix`, `chore` или `refactor`, — запрещён.
- Заголовок должен называть изменённый контракт или компонент и наблюдаемый результат, а не действие над файлами.
- Описывать результат в повелительной или инфинитивной форме, без точки в конце.
- Добавлять тело сообщения для причины, источника требования, существенного компромисса, миграции, эксплуатационного ограничения или причины отказа от альтернативы.
- В теле сообщения не пересказывать изменения; объяснять, почему изменение понадобилось и какие инварианты сохранены.
- Добавлять `BREAKING CHANGE:` только при реальном нарушении совместимости и описывать путь миграции.
- Не добавлять подписи, указание соавторов или упоминания об участии ИИ.

Примеры:

```text
feat(payments): добавить идемпотентную обработку
fix(api): сохранить ошибку конфликта при повторном запросе
refactor(worker): централизовать проверку доступа без смены поведения
ci(tests): сохранить обязательные проверки перед выпуском
```

## Создать коммит

Если по поручению нужно создать коммит, выполнить следующие шаги.

1. До записи в индекс проверить `git status`, `git diff --cached` и `git diff`. Зафиксировать содержание чужих staged-фрагментов в индексе и чужих unstaged-фрагментов в рабочем дереве для раздельного сравнения после коммита.
2. Для каждой семантической причины добавлять только принадлежащие ей файлы или фрагменты. Использовать точные пути, для смешанных файлов — выборочное добавление фрагментов; не выполнять `git add .`, `git add -A`, очистку или замену чужого индекса.
3. Выбрать способ фиксации по фактическому состоянию:
   - Если весь индекс содержит исключительно текущий кандидат, проверить `git diff --cached --check`, перечитать полный staged diff и создать обычный коммит. Не включать ещё не предназначенные для этого коммита собственные фрагменты.
   - Если в индексе есть другие изменения, а текущая причина состоит из целиком принадлежащих ей файлов без чужих или иных относящихся к другим причинам staged/unstaged-фрагментов на этих путях, проверить точный кандидат из рабочего дерева относительно HEAD (`git diff HEAD --check -- <пути>` и `git diff HEAD -- <пути>`; новые файлы сначала добавить точными путями). Допустимо использовать `git commit --only -- <пути>` с нужным сообщением: этот режим берёт содержимое указанных путей из рабочего дерева, а не только из индекса, и не включает остальные staged-файлы. Не применять его для смешанного файла.
   - Если выбранный кандидат требует частичных фрагментов, а индекс уже содержит изменения, не предназначенные для текущего коммита, использовать иной способ изоляции только при доказанной возможности сохранить чужие staged- и unstaged-фрагменты и рабочее дерево. Если безопасное выделение и проверка точного кандидата невозможны, остановить фиксацию и сообщить препятствие; не очищать чужой индекс, не переносить его изменения в свой коммит и не создавать обычный коммит со смешанным индексом.
4. Перед фиксацией убедиться, что кандидат соответствует одной причине и ранее проверенному изменению, а исходные условия не изменились параллельно. После коммита сверить его diff с кандидатом. Проверить, что в индексе сохранилось исходное содержание чужих staged-фрагментов, а в рабочем дереве — чужих unstaged-фрагментов. При расхождении остановиться и сообщить о нём. Историю переписывать только по отдельному поручению.
5. Повторить для остальных порученных независимых причин. Сообщить хеши, точные сообщения и оставшиеся staged-, unstaged- и неотслеживаемые изменения.
6. Не выполнять `push`, `rebase`, `reset`, `amend` или изменение истории без отдельного явного запроса.

## Проверить исходящие коммиты перед push

Выполнять этот раздел, если пользователь поручил отправку.

1. Определить исходную ревизию, удалённый репозиторий и целевую ветку по поручению и настройкам проекта. Проверить фактическую ревизию целевой ветки в удалённом репозитории. Для новой ветки определить согласованную базу, которая уже есть в этом репозитории.
2. Проверить весь диапазон командой `git log <цель-или-база>..<источник>` и сверить состав каждого исходящего коммита с поручением. Если в диапазон входят несвязанные коммиты, сначала выделить разрешённые изменения без перезаписи чужой истории. Если их нельзя безопасно выделить, сообщить причину и приостановить отправку.
3. Отправить проверенную ревизию в порученную ветку. После `push` проверить удалённую ветку и сообщить, какая ревизия опубликована.
