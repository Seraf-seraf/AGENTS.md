# Подготовка коммита

Соблюдать действующие общие и проектные инструкции.

Подготавливать коммит только по явному запросу пользователя.

## Изучить изменения

1. Проверить `git status`, изменения, добавленные и не добавленные в индекс Git.
2. Определить логическую причину и изменение контракта, а не перечислять файлы или повторять формулировку задачи.
3. Сопоставить реализацию, тесты, схему, конфигурацию, сгенерированные артефакты и документацию, относящиеся к одному поведению.
4. Отделить пользовательские и несвязанные изменения. Не включать их в индекс Git и не откатывать.
5. Если запрошен реальный коммит, убедиться, что релевантные проверки выполнены или явно сообщить, чего не удалось проверить.

Для изменения исполняемого CI/CD/IaC до коммита выполнить локальные проверки, выбранные по изменённому контракту и его потребителям по [CI/CD-навыку](../ci-cd/SKILL.md), сохраняя обязательные проверки проекта и порядок подготовки стабильного кандидата. Сообщение об ограничении не заменяет прохождение проверки или согласованное исключение. Успешную локальную проверку отличать от последующих подтверждений реального CI и тестового развёртывания; разрешение на коммит само по себе не разрешает отправку изменений в удалённый репозиторий или развёртывание.

## Определить границы коммита

- Один коммит должен иметь одну семантическую причину изменения, которую можно закончить фразой «чтобы …» без союза между независимыми целями.
- Реализацию и регрессионный тест одного поведения держать вместе.
- Разделять независимые исправления, переименования в API и конфигурации, изменения топологии и безопасности, зависимостей и сборки, форматирование и очистку кода.
- Не маскировать изменение поведения типом `refactor`. `refactor` допустим, только если неизменны наблюдаемый результат, ошибки, данные, API, контракт конфигурации и смысл правил безопасности.
- Если изменение одновременно исправляет дефект и перестраивает код, сначала выделить минимальное исправление поведения с тестом, затем отдельный рефакторинг с сохранением поведения, если история от этого становится понятнее.
- Перед добавлением в индекс Git перечислить точные файлы или фрагменты изменений каждого будущего коммита и проверить, что ни один файл не содержит смешанных причин.

## Сформировать сообщение

Использовать формат:

```text
type(scope): краткое действие на русском
```

- Выбирать из `feat`, `fix`, `refactor`, `test`, `docs`, `build`, `ci`, `chore`, `perf`.
- Указывать область изменения (`scope`), только когда она уточняет, к чему относится коммит.
- Заголовок, состоящий только из типа — `fix`, `chore` или `refactor`, — запрещён.
- Заголовок должен называть изменённый контракт или компонент и наблюдаемый результат, а не действие над файлами.
- Описывать результат в повелительной или инфинитивной форме, без точки в конце.
- Добавлять тело сообщения для причины, источника требования, существенного компромисса, миграции, эксплуатационного ограничения или причины отказа от альтернативы.
- В теле сообщения не пересказывать изменения; объяснять, почему изменение понадобилось и какие инварианты сохранены.
- Добавлять `BREAKING CHANGE:` только при реальном нарушении совместимости и описывать путь миграции.
- Не добавлять подписи, указание соавторов или упоминания об участии ИИ.

Примеры:

```text
feat(payments): добавить идемпотентную обработку
fix(api): сохранить ошибку конфликта при повторном запросе
refactor(worker): централизовать проверку доступа без смены поведения
ci(tests): сохранить обязательные проверки перед выпуском
```

## Создать коммит

Если пользователь попросил именно коммит:

1. Добавить в индекс Git только относящиеся к одной причине файлы или фрагменты изменений.
2. Проверить `git diff --cached --check` и перечитать изменения в индексе Git как самостоятельный набор изменений.
3. Создать один логический коммит, если пользователь не запросил другое разбиение.
4. Повторно проверить состояние рабочего дерева и сообщить хеш, точное сообщение и оставшиеся изменения вне индекса и неотслеживаемые файлы.
5. Не выполнять `push`, `rebase`, `reset`, `amend` или изменение истории без отдельного явного запроса.

Если пользователь попросил только сообщение, не изменять индекс или историю Git.
