# Makefile, Docker, shell и локальная проверка CI

Применять разделы для инструментов, участвующих в изменённом пути исполнения. Общий порядок обязательных проверок брать из основного навыка.

## Совместимость и подготовка

- Для новой возможности инструмента проверить поддержку у всех исполнителей соответствующей конфигурации: локально, на runner и целевом хосте. Получить фактическую версию той команды, которая запускается под рабочим пользователем; наличие бинарника само по себе не подтверждает совместимость. Нужную версию обеспечивать существующим механизмом подготовки среды.
- Собственный разбор машинного вывода проверять на корректных результатах используемых версий инструмента и на отрицательных сценариях. Учесть defaults, пропущенные поля и нормализацию по документированному контракту. Если преобразование теряет нужное свойство, проверять его по сохраняющему это свойство представлению; не ослаблять отклонение действительно неверного ввода.
- Новый или сокращённый режим подготовки выполнить с чистого checkout, без ранее созданных runtime-каталогов, volumes и маркеров готовности. Затем запустить его непосредственного потребителя без предварительного полного bootstrap. Проверить повторное применение отдельно: работа в подготовленной среде доказывает только повторный путь. Изолировать очистку от рабочих данных пользователя.
- Доступ к внешнему ресурсу подтвердить минимальной операцией из процесса-потребителя, включая его UID/GID, дополнительные группы, mounts и окружение. Это требуется и при подключении нового ресурса с прежним пользователем; проверка из shell хоста или от root не подтверждает доступ приложения.

## Локальная проверка pipeline

- Для GitHub Actions использовать принятую проектом семантическую проверку workflow; при её отсутствии — [actionlint](https://github.com/rhysd/actionlint). Проверять выражения, входы/выходы и зависимости jobs; YAML parser подтверждает только синтаксис YAML.
- Для GitLab применять штатные проверки и [CI Lint](https://docs.gitlab.com/ci/yaml/lint/) с includes и контекстом проекта. CLI/API обращаются к GitLab: это сетевая проверка, а симуляция создания pipeline не исполняет jobs. Изменённые includes должны входить в проверяемую конфигурацию; ссылка на прежнюю версию файла не проверяет локальные изменения. Недоступную серверную проверку обозначить отдельно.
- Локально выполнять те же команды проекта с сопоставимыми инструментами и зависимостями, которые вызывает CI. Сначала искать существующий Makefile, скрипт или иной штатный entrypoint. Не создавать второй набор команд специально для локального прогона.
- Использовать локальный эмулятор pipeline, если он принят в проекте, с учётом его ограничений. Например, [act](https://nektosact.com/not_supported.html) не подтверждает поведение permissions, concurrency и environment secrets. Успех эмулятора не закрывает эти проверки в реальной CI-системе.

## Makefile

- Существующий Makefile использовать как основной интерфейс типовых операций. Сначала искать готовую цель; новую добавлять только для повторяемого сценария.
- Цели без файлового результата объявлять `.PHONY`.
- Не прятать в цели необратимые операции и изменения окружения пользователя: назначение должно быть явно видно из имени, а выполнение — разрешено задачей.

## Docker

- При создании или изменении сборки image предпочитать multi-stage build, небольшой runtime image, непривилегированного пользователя, `.dockerignore` и явно зафиксированные версии базовых образов. Изменение Compose wiring не требует попутной перестройки Dockerfile.
- Не помещать секреты в image, Dockerfile, build arguments или репозиторий. Конфигурацию передавать во время запуска.
- При изменении image проверять точный `CMD`/entrypoint, production-зависимости, минимальный запуск и затронутое health behavior. При подключении готового image проверять его интеграцию через существующий Compose и runtime-конфиг; не компилировать заново согласованную готовую поставку.
- Для Compose учитывать, что [`config`](https://docs.docker.com/reference/cli/docker/compose/config/) объединяет источники, подставляет переменные и нормализует модель. Выбирать представление для проверяемого свойства; вывод с подставленными секретами не печатать и не сохранять в artifacts.

## Shell-скрипты сборки и доставки

- Использовать shell, заявленный средой и проектом. Для POSIX `sh` сохранять совместимый синтаксис и `set -eu`; не навязывать POSIX другим языкам или runtime.
- Заключать expansion переменных в кавычки; обязательные входы проверять до мутаций, для обязательных непустых переменных использовать `${VAR:?}`. Ожидаемые ненулевые коды обрабатывать явно.
- Передавать внешние входы через аргументы или документированные переменные окружения; не полагаться на случайные локальные значения.
- Выполнить `shellcheck` для изменённых скриптов с учётом их диалекта и, когда применимо, безопасный запуск с минимальными test inputs. Если инструмент недоступен, сообщить это ограничение.
- Исключение lint-правила сопровождать комментарием с технической причиной и областью действия.
