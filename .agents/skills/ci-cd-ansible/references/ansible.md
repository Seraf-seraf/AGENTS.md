# Ansible: условные правила исполнения

Применять только к Ansible-части задачи. Общий контракт доставки и критерии проверки брать из основного навыка.

## Структура и состояние

- Оставлять playbook точкой сборки: hosts, входы и роли. Объединять в роли одну инфраструктурную ответственность; не копировать один lifecycle между deploy и rollback.
- Значения по умолчанию хранить в defaults, параметры среды — в inventory. Секреты получать из защищённого источника.
- При файловых проверках явно выбирать object type и смысл follow: проверяется ссылка или её цель. Не считать наличие пути доказательством доступности нужного объекта.
- Прежде чем размножать изменённый task pattern, проверить один полный экземпляр parser-ом и доступными Ansible-проверками.

## Identity и prerequisites

1. Для каждой изменённой фазы определить remote_user/ansible_user, become_user и фактического владельца файлов и процессов. Отделить системные операции от application lifecycle.
2. Проверить не только SSH и право sudo, но и передачу и выполнение реального безопасного Ansible module под нужной парой пользователей.
3. При переключении между непривилегированными пользователями выбрать поддерживаемый механизм доступа к временным module-файлам. Для POSIX ACL проверить утилиты и поддержку файловой системой; одного NOPASSWD недостаточно.
4. Установить prerequisites transport и become через уже работоспособный bootstrap-путь до первой зависимой task. Не готовить механизм через тот же путь, который без него не работает.
5. Не расширять весь play до root ради одной операции. Проверять ownership, home/cache, sockets и credentials затронутых фаз после смены identity.

## Tasks и проверка

- Использовать полные имена модулей. Для command предпочитать argv; shell выбирать только при необходимости его возможностей.
- Явно задавать changed_when и failed_when там, где стандартный результат не отражает нужную семантику. Не использовать ignore_errors для сокрытия отказа; допустимые исходы обрабатывать явно.
- Давать tasks содержательные имена, register/facts — имена с областью ответственности; modes задавать строками.
- Для операций с секретами использовать no_log; наружу выводить только безопасную диагностику.
- Для изменённых YAML и Ansible выполнить доступные YAML parser, `yamllint`, `ansible-lint` и `ansible-playbook --syntax-check` с относящимися к задаче playbook и inventory. Проверки не заменяют друг друга; недоступные инструменты указать в ограничениях. После изменения identity или transport отдельно выполнить безопасный module в представительной среде: syntax-check этого не подтверждает.
