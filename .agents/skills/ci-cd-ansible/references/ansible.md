# Ansible: условные правила исполнения

Применять только к Ansible-части задачи. Общий контракт доставки и критерии проверки брать из основного навыка.

## Структура и состояние

- Следовать существующей структуре. Роль выделять для целостной инфраструктурной ответственности, которую нужно отдельно сопровождать или переиспользовать. Небольшая задача допустима прямо в playbook; отдельная роль на каждую фазу или несколько строк не нужна.
- Описывать желаемое состояние штатными модулями `user`, `file`, `package`, `copy`, `template`, `systemd_service` и подходящими модулями коллекций. Не писать собственную последовательность обнаружения и исправления состояния, которое уже обеспечивает модуль.
- Defaults роли хранить в `defaults`, различия окружений — в inventory; секреты получать из защищённого источника. Константы держать внутри реализации, производные пути вычислять из одного корня. `extra_vars` оставлять для реальных входов запуска; не дублировать ими весь inventory.
- Не превращать каждый литерал в параметр с последующим `assert`, требующим прежнее фиксированное значение. Сохранять существующие внешние параметры до отдельно разрешённого изменения их контракта.
- Для конфигурации использовать `copy` или `template`, при наличии штатного validator — `validate`; перезапускать или перечитывать конфигурацию handler-ом только при изменении. Формат прикладного конфига и операции над прикладными данными остаются у сервиса.

## Проверки внутри playbook

- Оставлять проверку, если её результат нужен для безопасного действия, выбора ветки или подтверждения готовности: обязательный внешний вход, опасная цель удаления, чужой ресурс, работоспособность сервиса. Не добавлять проверки только для подтверждения того, что агент правильно написал tasks.
- Доверять результату штатного модуля в пределах его контракта. Не окружать каждую установку цепочкой `stat → assert → действие → stat → assert`; отсутствие каталога, который playbook должен создать, само по себе не ошибка.
- Дополнительную проверку обосновывать иной границей или свойством, которое модуль не обеспечивает. Например, корректный синтаксис nginx-конфига не доказывает доступность приложения через ingress.
- Когда файловая проверка нужна, явно выбирать тип объекта и `follow`: ссылка или её цель. Не заменять проверку опасной цели предположением о наличии пути.
- Проверки качества инфраструктурного кода выполнять в тестах/CI, временную диагностику — в `/tmp/`. Не переносить тот же набор самопроверок в постоянный shell-скрипт.

## Identity и prerequisites

При изменении identity или transport проследить `ansible_user`, `become_user` и владельцев файлов/процессов. Подтвердить передачу и выполнение безопасного module под затронутой парой пользователей: SSH и NOPASSWD не доказывают доступ к временным module-файлам. При переключении между непривилегированными пользователями проверить выбранный механизм доступа, например POSIX ACL.

Prerequisites transport и become устанавливать через уже работающий bootstrap-путь до первой зависимой task. Не расширять весь play до root ради одной операции. Эти проверки среды не требуют постоянного identity/preflight playbook, если он не нужен эксплуатации.

## Tasks и проверка

- Использовать полные имена модулей. Для command предпочитать argv; shell выбирать только при необходимости его возможностей.
- Задавать `changed_when` и `failed_when`, когда стандартный результат не отражает нужную семантику. Не повторять стандартный отказ по ненулевому коду и не скрывать изменения через безусловный `changed_when: false`. Не использовать `ignore_errors` для сокрытия отказа; допустимые исходы обрабатывать явно.
- Давать plays, tasks и handlers содержательные русские имена; `register`/facts — имена с областью ответственности; modes задавать строками. Не создавать `set_fact` только ради переименования уже доступного значения.
- Для операций с секретами использовать no_log; наружу выводить только безопасную диагностику.
- Запустить обязательные проверки проекта для затронутых файлов. `ansible-lint` уже выполняет syntax-check для playbooks; отдельный `ansible-playbook --syntax-check` нужен, если playbook не покрыт или требуется другой inventory/контекст. Отдельный YAML parser нужен для непокрытых файлов, а не автоматически как ещё один gate.
- При изменении управления состоянием проверить повторное применение в изолированной представительной среде: без новых изменений и лишних рестартов. `--check` помогает, но не доказывает идемпотентность реального исполнения. Не добавлять Molecule или новую тестовую инфраструктуру ради каждой локальной правки. Недоступные проверки указать явно.
