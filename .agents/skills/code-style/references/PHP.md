# Стиль PHP-кода backend

## Применимость

PHP: `.php` и PHP-фрагменты шаблонов, включая `.blade.php`. В смешанном шаблоне применять этот файл только к PHP; HTML/CSS и JavaScript проверять по соответствующим справочникам. Правила FormRequest, Eloquent, Laravel Resources и Filament относятся к проектам, использующим эти инструменты; они не требуют добавлять Laravel в другой PHP-проект.

Этот справочник содержит согласованные пользователем правила оформления и корректности PHP-кода. Они применяются вместе с существующими инструкциями проекта. Порядок приоритетов задан в [Code Style](../SKILL.md): проектные правила выше локальных дополнений этого файла, а локальные дополнения выше внешнего стандарта. Проверки типов и DTO — явные требования пользователя, а не гарантии форматтера и не повод переносить общий процесс архитектурного ревью или тестирования в этот справочник.

## Базовый стиль и конфигурация проекта

В Laravel-проекте базовый стиль задаёт Laravel Pint с пресетом `laravel` и конфигурацией `pint.json`. Настройки отступов, конца строки и пробелов находятся в `.editorconfig`. Пресет Laravel близок к PSR-12, но не является его точной копией. Явно выбранные настройки конкретного проекта сохраняют приоритет.

Перед работой прочитать существующие `CODESTYLE.md`, `pint.json` и `.editorconfig` в PHP-проекте. Если backend расположен в `apps/backend`, это `apps/backend/CODESTYLE.md`, `apps/backend/pint.json` и `apps/backend/.editorconfig`. Это пути рабочего проекта, не относительные ссылки на файлы внутри плагина. Если структура другая, использовать её фактические пути; не создавать отсутствующую конфигурацию без поручения.

Из каталога PHP-приложения форматирование можно проверить командой `vendor/bin/pint --test`, а применить командой `vendor/bin/pint`. Для структуры с `apps/backend` команды выполняются из этого каталога. Команды требуют установленных Composer-зависимостей; их также можно запустить в контейнере приложения из его фактического рабочего каталога — например, `/var/www/html`, если он так настроен. Не предполагать существование контейнера или этих путей в любом проекте. Перед массовым применением учитывать незакоммиченные изменения; не переформатировать соседний код без поручения.

В PHP-проекте без Pint сохранять его существующий formatter/linter и применимые правила этого файла; не устанавливать Laravel или Pint автоматически.

## Дополнительные правила читаемости

- Массив с несколькими элементами оформляйте в несколько строк: один элемент на строку, вложенные массивы — с тем же правилом. После последнего элемента многострочного массива ставьте запятую. Одноэлементный и пустой массивы могут оставаться однострочными.
- В цепочке ORM-запроса каждый последующий вызов размещайте на отдельной строке с отступом. В других длинных цепочках используйте переносы, когда они улучшают читаемость.
- В вызовах функций и методов, конструкторах и объявлениях функций и методов с тремя и более аргументами или параметрами размещайте каждый аргумент или параметр на отдельной строке. В уже многострочных списках с меньшим количеством элементов также используйте по одной строке на элемент. Длинные условия разбивайте по логическим частям; используйте ранний возврат, когда это делает код понятнее и сохраняет порядок вычислений, побочные эффекты и результат.
- В многострочных составных условиях `if` размещайте открывающую и закрывающую скобки на отдельных строках относительно логических частей: строка `if (`, затем логические части по одной на строке с оператором в начале продолжения, затем строка `) {`, как в примере ниже. Короткий вызов `in_array` с простыми аргументами внутри такого условия допускается записывать в одну строку, в том числе с тремя аргументами.
- Полные имена классов и пространств имён в коде и PHPDoc выносите в импорты `use` в начале файла. При совпадении коротких имён используйте алиасы, сохраняющие исходное разрешение классов.
- Для оптимизируемых встроенных PHP-функций, вызываемых из пространства имён, используйте `use function` глобальной функции, если проверено, что не требуется одноимённая функция этого пространства имён. В глобальном пространстве имён такой импорт не нужен. Не меняйте разрешение пользовательских функций ради форматирования.
- Параметры и возвращаемые значения функций и методов типизируйте явно согласно инструкциям проекта и возможностям используемой версии PHP. У конструктора указываются типы параметров, но не возвращаемый тип.

### Примеры оформления

Многоэлементные массивы и ORM-цепочки:

```php
$statuses = [
    'active',
    'reserved',
];

$items = CatalogItem::query()
    ->where('is_active', true)
    ->orderBy('id')
    ->get();
```

Три и более параметра или аргумента вне составного условия:

```php
function updateItem(
    int $id,
    string $name,
    bool $active,
): void {
    saveItem(
        $id,
        $name,
        $active,
    );
}
```

Многострочное составное условие и ранний возврат:

```php
if (
    ! is_string($code)
    || ! in_array($code, $allowedCodes, true)
) {
    return;
}
```

Импорты классов и проверенных глобальных функций в файле с пространством имён:

```php
use App\Models\CatalogItem;
use Other\CatalogItem as ExternalCatalogItem;

use function in_array;
use function is_string;
```

Примеры — фрагменты соответствующего файла, не самостоятельное приложение; используемые классы импортируются в начале этого файла.

### Что проверяет Pint и что остаётся для ревью

Pint проверяет базовый пресет и настроенные правила отступов цепочек, многострочных аргументов и массивов. Конкретный набор гарантий определяется прочитанной конфигурацией `pint.json` и установленной версией инструмента; не считать `.editorconfig` автоматическим источником всех настроек Pint.

Pint сам по себе не обеспечивает порог в три аргумента или параметра, обязательный перенос каждого элемента массива и вызова ORM во всех случаях, а также не проверяет безопасность импорта функций. Эти правила проверяют при работе с кодом и ревью; успешный запуск форматтера не заменяет такую проверку.

Правило PHP-CS-Fixer `native_function_invocation` автоматически добавляет глобальный префикс и может изменить разрешение переопределённой функции. Поэтому не включать его автоматически. Проверенные точечные импорты `use function` не разрешают массовое изменение разрешения функций.

## Типы должны обеспечиваться исполняемым кодом

PHPDoc не заменяет проверку типа. Запрещено использовать аннотации, чтобы объявить непроверенное значение корректным для анализатора.

Типы обеспечиваются:

- нативными типами параметров, свойств и возвращаемых значений;
- проверками `instanceof`, `is_string`, `is_int`, `is_array` и другими подходящими проверками;
- DTO с типизированными свойствами и проверяемым созданием;
- явной проверкой состава коллекций, обязательных полей, nullable-значений и диапазонов.

PHPDoc допустим как описание контракта, который уже обеспечен кодом. Прохождение статического анализа само по себе не доказывает наличие runtime-проверки.

## Проверять данные на границе

Данные запроса, формы, JSON, БД, кэша и внешнего API проверяются до использования в прикладном коде.

Проверка должна соответствовать используемому контракту:

- `is_array()` проверяет контейнер, но не его элементы;
- `array_is_list()` проверяет последовательность ключей, но не тип элементов;
- `instanceof` проверяет класс объекта;
- обязательность поля и допустимость `null` проверяются отдельно;
- числовой тип и допустимый диапазон проверяются отдельно.

Приведение `(int)`, `(string)`, `(array)` и другие преобразования не считаются валидацией. Преобразовывать значение можно после проверки допустимого исходного представления.

`assert()` не используется для обязательной проверки входных данных: assertions могут быть отключены. `strict_types=1` не заменяет проверку структуры массивов и коллекций.

## Объекты проверять через instanceof

Не допускается:

```php
/** @var User $user */
$user = $request->user('customer');

return $user->email;
```

Следует:

```php
$user = $request->user('customer');

if (! $user instanceof User) {
    throw new AuthenticationException();
}

return $user->email;
```

Исключение и способ представления ошибки выбираются по существующему контракту операции.

То же правило применяется к `$resource` в Laravel Resources и к результатам связей Eloquent. Для nullable-связи отсутствие записи обрабатывается отдельной допустимой веткой.

## Структурированные данные передавать через DTO

Данные формы или другого внешнего источника с известной структурой преобразуются в DTO на входной границе. Прикладной код принимает DTO вместо массива с описанием структуры в PHPDoc.

Не допускается:

```php
/** @var array{length_cm:int|string, weight_g:int|string} $data */
$data = $request->validated();

$service->execute($data);
```

Следует:

```php
$data = PackageData::fromInput($request->validated());

$service->execute($data);
```

Пример проверяемого DTO:

```php
final readonly class PackageData
{
    private function __construct(
        public int $lengthCm,
        public int $weightG,
    ) {}

    public static function fromInput(mixed $input): self
    {
        if (! is_array($input)) {
            throw new InvalidArgumentException('Package must be an array.');
        }

        return new self(
            self::positiveInteger($input['length_cm'] ?? null, 'length_cm'),
            self::positiveInteger($input['weight_g'] ?? null, 'weight_g'),
        );
    }

    private static function positiveInteger(
        mixed $value,
        string $field,
    ): int {
        if (! is_int($value) && ! is_string($value)) {
            throw new InvalidArgumentException("$field must be an integer.");
        }

        $parsed = filter_var(
            $value,
            FILTER_VALIDATE_INT,
            ['options' => ['min_range' => 1]],
        );

        if ($parsed === false) {
            throw new InvalidArgumentException(
                "$field must be a positive integer.",
            );
        }

        return $parsed;
    }
}
```

В примере допустимы целое число и его строковое представление из формы. Допустимые представления и верхние границы определяются контрактом конкретного поля. Это пример для PHP с поддержкой `readonly class`; в проекте сохранять его версию PHP и обеспечивать те же инварианты доступными средствами, не обновляя runtime ради примера.

DTO не должен быть обёрткой вокруг непроверенного массива. Вложенные структуры получают собственные DTO, а списки проверяются поэлементно. Для списков также проверяется `array_is_list()`, если последовательные ключи являются частью контракта.

Существующие DTO и парсеры переиспользуются. Новая библиотека или отдельный класс не требуются для каждого локального значения.

## Сохранять границы ответственности

Не писать валидацию в контроллерах. В Laravel этап валидации HTTP-запроса писать в связанном FormRequest.

Laravel FormRequest и Filament отвечают за представление ошибок формы. Прикладные DTO не зависят от HTTP, Livewire или ORM.

Проверка формы и создание DTO должны использовать согласованные правила. Уже выполненную проверку не следует копировать по всем слоям. При этом публичный путь создания DTO не должен позволять обойти его инварианты.

SQL-проекции проверяются и преобразуются в инфраструктурном адаптере. JSON декодируется с проверкой структуры: успешный `json_decode()` подтверждает только корректность JSON.

При чтении из кэша проверяется фактически полученное значение. Наличие ранее проверенного производителя не доказывает корректность текущей записи кэша.

## Использовать PHPDoc только для обеспеченных контрактов

Допустимы:

- пояснения назначения, единиц измерения и ограничений;
- generic-аннотации коллекций, связей и фабрик, описывающие обеспеченный кодом контракт;
- сигнатуры callback, когда их входы и результаты действительно соответствуют описанию.

Например:

```php
/** @return BelongsTo<TagGroup, $this> */
public function group(): BelongsTo
{
    return $this->belongsTo(TagGroup::class, 'tag_group_id');
}
```

Эта аннотация описывает связь для анализатора. При чтении результата связи код должен обеспечить требуемый тип модели перед использованием.

Локальный `@var`, который лишь переобъявляет тип значения из `mixed`, удаляется и заменяется исполняемой проверкой. Если тип уже выводится из кода, избыточная аннотация удаляется без добавления искусственных проверок.

## Проверять успешные и ошибочные данные

При добавлении проверяемой границы тестами покрываются применимые случаи:

- корректные данные и прежний результат операции;
- отсутствие обязательного поля;
- разрешённый и запрещённый `null`;
- неверный scalar или класс объекта;
- неверный элемент внутри коллекции;
- список с неправильными ключами;
- граничные значения диапазонов;
- отказ до побочных эффектов.

Для рефакторинга сохраняются сериализация, ошибки, авторизация, денежная точность, идемпотентность и транзакционное поведение.

Изменения должны проходить PHPStan на принятом уровне проекта. Запрещено компенсировать отсутствие проверок новыми утверждениями `@var`, подавлениями ошибок, расширением baseline или снижением уровня анализа.

Проверки выполнять по [навыку проверки изменений](../../verify-change/SKILL.md), ревью — по [архитектурным критериям Software Engineering](../../analyze-change/references/architecture.md) в пределах поручения. В проекте с Makefile тесты запускать его штатными целями; точечные тесты запускать тем же способом, с теми же настройками и в той же среде, которые заданы Makefile. Имена целей и команды анализа брать из проекта, не придумывать. Отсутствие нужного инструмента сообщать как ограничение проверки, а не как успешный результат.
