# Code Style

Соблюдать общие инструкции и границы поручения. Этот навык отвечает за оформление, именование, языковые конструкции и явно заданные в справочнике правила корректности. PHP-справочник дополнительно содержит согласованные пользователем правила runtime-типов, DTO, PHPDoc и валидации. Общий процесс архитектурного разбора, тестирования, сборки и ревью остаётся у профильных навыков; языкоспецифичные требования применяются вместе с ними. Проверка стиля сама по себе не разрешает менять код.

## Выбрать справочник

Определить язык по содержимому и фактически создаваемым, изменяемым или проверяемым файлам. Для скрипта без расширения учитывать shebang; расширение не должно подменять фактический язык.

| Язык и файлы | Справочник |
| --- | --- |
| JavaScript: `.js`, `.mjs`, `.cjs`, `.jsx`; TypeScript: `.ts`, `.mts`, `.cts`, `.tsx` | [JS_TS.md](references/JS_TS.md) |
| PHP: `.php`, PHP-фрагменты `.blade.php` | [PHP.md](references/PHP.md) |
| Go: `.go` | [GO.md](references/GO.md) |
| Python: `.py`, `.pyi`, скрипты Python | [PYTHON.md](references/PYTHON.md) |
| Java: `.java` | [JAVA.md](references/JAVA.md) |
| Shell: `.sh`, `.bash`, скрипты Bash | [SHELL.md](references/SHELL.md) |
| HTML: `.html`, `.htm`; CSS: `.css` | [HTML_CSS.md](references/HTML_CSS.md) |

В смешанном проекте читать только справочники затронутых языков. В шаблоне или компоненте с несколькими языками учитывать изменяемые фрагменты. JSX/TSX направлять в JS_TS.md, CSS-фрагменты — в HTML_CSS.md; PHP-фрагменты Blade — в PHP.md, остальные части шаблона — в соответствующие справочники. Не выдавать HTML-правила за правила JSX или правила PHP за синтаксис Blade. Справочник JS_TS.md содержит отдельные источники для обоих языков: выбирать относящиеся разделы, учитывать отличия TypeScript.

Примеры выбора: `.ts` и `.tsx` → JS_TS.md; `.go` → GO.md; изменение `.ts` и `.css` → только JS_TS.md и HTML_CSS.md. `.php` → PHP.md; изменение PHP и HTML в `.blade.php` → PHP.md и HTML_CSS.md. Laravel-специфичные требования PHP.md не требуют добавлять Laravel в другой PHP-проект.

## Применить приоритеты

1. Явные правила конкретного проекта, включая formatter/linter-конфигурацию.
2. Явные локальные дополнения выбранного языкового файла.
3. Внешний стандарт, точно указанный в этом файле.

Прочитать выбранный справочник. Краткие правила и примеры не заменяют весь стандарт: при спорном решении или новом соглашении читать нужный раздел указанного источника, а не весь документ при каждой правке. Отмечать конфликт и применять более высокий приоритет. Если конфликт не разрешается этим порядком и меняет результат, уточнить только зависимую часть.

Различать три ситуации:

- **Нет языкового файла:** работать по правилам проекта; не загружать чужой язык, не искать и не назначать неизвестный стандарт автоматически. Новый язык добавлять по поручению: определить точные источники и расширения, создать справочник по общей структуре и обновить таблицу.
- **Указанная ссылка недоступна:** использовать доступные проектные правила и подтверждённые положения справочника; обозначить непроверенную часть. Не выдавать непрочитанный источник за проверенный и не подбирать замену автоматически.
- **Правила конфликтуют:** применять порядок выше; локальные дополнения отличать от требований внешнего стандарта.

## Проверить результат

Проверить затронутое оформление штатным formatter/linter проекта, если он предусмотрен; явно заданные языковые требования корректности проверять по соответствующему справочнику и навыку проверки изменений, не считать успех форматтера их подтверждением; не устанавливать новые инструменты ради этого навыка. Для ручной проверки сверить только относящиеся правила и примеры. Не переформатировать соседний код без поручения. Сообщить существенные конфликты, отсутствие стандарта или ограничения проверки, если они влияют на результат.
