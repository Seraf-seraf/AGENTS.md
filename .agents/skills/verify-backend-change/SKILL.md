# Verify Backend Change

Проверять согласованное изменение минимальным достаточным набором действий. Для рефакторинга подтверждать сохранение поведения, а не искать повод для новых исправлений.

## Определить область проверки

1. Изучить запрос, diff, локальные инструкции и существующие цели `Makefile`; manifest и lock-файлы читать, когда проверка зависит от них. Зафиксировать границы задачи и явные исключения пользователя.
2. Сформулировать contract delta: источник истины, наблюдаемое поведение, inputs/outputs, units, boundaries, errors, authorization и compatibility.
3. Классифицировать изменение: behavior fix/feature, behavior-preserving refactor, public contract, config, dependency, data/migration или infrastructure. Не принимать название коммита за доказательство типа изменения.
4. Сопоставить изменённые ветви бизнес-логики с существующими тестами, публичными контрактами и всеми producer/consumer.
5. Начать с самой узкой проверки и расширять её только для проверки затронутого поведения или контракта. Пункты ниже применять по необходимости; структурный рефакторинг не требует автоматически запускать полный аудит, БД, E2E или deploy.
6. При запросе только на проверку не менять код. Не оспаривать принятые архитектурные исключения и единого владельца политик без подтверждённого нарушения.

## Проверить достаточность структуры изменения

Применять, когда diff добавляет, меняет или удаляет сервис, port, adapter либо границу компонента; не превращать локальный fix в архитектурный аудит.

- Проверить, что локальное условие, вычисление или преобразование не обросло новым слоем без необходимости; сначала рассмотреть чистую функцию и существующий сервис/reader/port с подходящим контрактом.
- Для нового сервиса проверить собственную ответственность в одном контексте: прикладную координацию, бизнес-решения, политики, транзакцию или lifecycle. Не переносить в него чужие политики и не принимать pass-through обёртку за самостоятельную ответственность.
- Для нового port найти конкретного потребителя, реальную границу и нежелательную зависимость от технологии, vendor API или чужой реализации. Проверить, почему существующий контракт и более простая правка недостаточны. Краткого конкретного обоснования достаточно; не требовать архитектурного отчёта для обычного fix. DI, удобство mock или предположение о будущей замене сами по себе недостаточны.
- Проверить consumer-owned семантику контракта, отсутствие непредусмотренной утечки SDK/ORM/transport types, mapping результатов и ошибок в adapter и wiring в composition root по правилам проекта. Сервис может использовать port, а один production adapter допустим; не требовать второго провайдера или интерфейса для каждого класса.
- При удалении или обходе существующей границы проверить, что не возвращены нежелательные технологические зависимости в core и не смешаны владельцы данных, политик, транзакций и lifecycle. Сокращение файлов и единственный adapter сами по себе не доказывают улучшение.
- Подтверждать поведение на затронутой границе: consumer contract, реальный adapter/mapping и релевантный failure path, если они изменены. Использовать существующие проверки; зелёный mock-тест не доказывает соответствие adapter контракту. Не добавлять дублирующие DTO, обёртки и постоянные проверки количества классов ради самого изменения структуры.

## Зафиксировать регрессию или поведение

- Для дефекта подтвердить требование независимо от предлагаемого исправления и получить падающий тест или воспроизводимый scenario, который отличает ошибочное поведение от правильного. Проверить причину падения: она должна соответствовать заявленному дефекту.
- Для рефакторинга до правок выполнить существующие проверки сохраняемого поведения; добавить characterization tests только для недостающего существенного покрытия. После правок повторить те же проверки. Не требовать искусственного падения теста там, где поведение должно остаться прежним.
- Сопоставить до и после результаты, errors/status codes, права, сериализацию, значимый порядок side effects, транзакции, блокировки, отмену и повторы. Смена public API, схемы, configuration contract, security model или топологии развёртывания требует отдельного разрешения, а не только типа коммита.
- Если проверка начата после реализации, использовать доступную исходную версию без отката пользовательской работы. Если сравнение с исходным поведением недоступно, сообщить ограничение и не заявлять, что эквивалентность подтверждена.
- Не менять ожидаемый результат теста только потому, что новая реализация возвращает другое значение. Сначала подтвердить изменение требования или контракта.
- Реализацию и регрессионный тест одного поведения проверять вместе; независимые изменения не маскировать одним зелёным suite.
- Сначала использовать существующее покрытие. Одноразовые проверки строк, импортов и факта изменения хранить вне репозитория, не добавлять в stage. Постоянный тест должен защищать значимое поведение, контракт или регрессию.

## Выполнить проверки

- Использовать штатные команды проекта; не создавать временный runner без необходимости.
- Запустить релевантные unit или integration tests, затем type check или build, если изменение зависит от них.
- Для алгоритмического лимита проверить `N-1`, `N`, `N+1`, пустой input, oversized элемент, пересечение внутренних границ, повтор и детерминированность. Указывать единицы измерения в test names или test data.
- Для lifecycle проверить разрешённые и запрещённые transitions, concurrent call, replay, timeout/cancel и failure до и после первого side effect.
- Для error mapping проверить outward code/status/retryability для known domain/conflict errors отдельно от unknown infrastructure failure.
- Для authorization проверить allow и deny по каждой затронутой action, отсутствие обхода через соседний endpoint и привязку grant/context к actor, resource и action.
- Для public API, GraphQL или message schema найти canonical definition и проверить совместимость scalar/type, nullability, enum, names и consumer serialization.
- Для config/env rename найти все readers, writers, examples, deployment templates и docs. Отдельно проверить, что rename не изменил значение, endpoint, topology или security semantics.
- Для новой runtime dependency проверить manifest, lock-file, production package/image, фактический entrypoint и запуск с production-only dependencies.
- Для внешнего сервиса или offline asset проверить preflight и отличить unavailable environment от application defect.
- Для логирования проверить наличие безопасного structured context и отсутствие credentials, secrets, необезличенного пользовательского текста и полного external payload.
- Проверять path, cwd, symlink semantics, permissions и environment в том context, где реально исполняется код, а не только в локальном shell.
- Запускать formatter и lint только для изменённых файлов или строк, когда инструмент это поддерживает.
- Не исправлять и не форматировать несвязанный код.
- Если падение существовало до изменения, подтвердить это и отделить его от новой регрессии.
- Перед признанием дефекта указать место, источник требования и достижимый сценарий либо статическое доказательство нарушения. Проверить опровергающие факты в вызывающем коде, валидации и принятых исключениях. Недоступное окружение, предпочтение или гипотеза не являются доказанным дефектом.
- Если подтверждён дефект текущего изменения и задача разрешает реализацию, внести минимальное исправление в её границах и повторить затронутые проверки. При рефакторинге восстанавливать исходное поведение, если правка внесла регрессию; не исправлять попутно старые ошибки и не менять исходный контракт.

## Проверить данные

Когда затронутое поведение требует проверки с БД:

1. Использовать только изолированную локальную или test БД.
2. Создать минимальные временные данные через уже существующий API, factory, fixture-механизм или точный SQL.
3. Проверить каноническое business field и пограничные записи, которые surrogate-фильтр по времени, статусу или косвенному признаку мог бы ошибочно исключить.
4. Для stateful операции проверить итоговое состояние всех затронутых записей после success, conflict, timeout и partial failure.
5. Не изменять shared, staging или production БД без отдельного явного запроса.
6. Не добавлять постоянный seeder или fixture только ради разовой проверки.
7. Удалить временные данные, если они не откатываются транзакцией или сбросом test-окружения.

Если окружение недоступно, подготовить точные входные данные и команды, но не утверждать, что проверка выполнена.

## Проверить test topology

- Убедиться, что изменённый тест входит хотя бы в один обязательный suite и не попадает случайно в несколько одинаковых suites.
- Если suite требует БД, containers, browser или внешнюю сеть, проверить capability назначенного runner.
- Не считать release защищённым тестом, который больше не находится в gate graph.
- Не отключать или исключать падающую обязательную suite ради зелёного pipeline без явного risk acceptance, срока и компенсирующей проверки.

## Подготовить ручную GraphQL-проверку

Если изменены поведение или публичный контракт GraphQL, привести в финальном ответе готовый `query` или `mutation` и отдельный JSON с variables. Использовать реальные имена и types из схемы, проверив их в canonical definition; не придумывать поля и scalar. Не добавлять операцию к чисто структурной проверке без запроса.

## Отчитаться и завершить

Кратко сообщить результат, какие контракты или сохраняемое поведение проверены, какие команды действительно выполнены и что они показали. Отдельно отметить существенные ограничения, невыполненные проверки и подтверждённые предсуществующие сбои. Не выдавать предположительную причину падения за установленную и не писать «всё проверено» по одному зелёному suite.

Оставшиеся подтверждённые ошибки перечислить без дублей: **место → требование и подтверждение → минимальное исправление**. Потенциальные риски и предпочтения не смешивать с ошибками; включать их только по запросу. При отсутствии подтверждённых дефектов прямо сообщить об этом, не объявляя всю систему безошибочной.

Данные, producer/consumer, production artifacts и ручную GraphQL operation указывать только когда они относятся к выполненной проверке. После проверки согласованной области и исправлений завершить работу; не начинать новый проход самостоятельно без изменения относящегося к ней кода, предпосылок или появления новых данных.
