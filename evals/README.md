# Испытания поведения Software Engineering

Набор переводит 26 калибровочных сценариев в воспроизводимые задачи: 16 сценариев разбора изменений и 10 сценариев планирования. Каждая задача получает маленький проект с исходниками, контрактом и штатными проверками. Проверяющий получает отдельные критерии и фактические результаты работы.

Наличие сценариев и зелёные тесты runner не означают, что модель прошла эти сценарии. Прохождение фиксируется отдельно для конкретных инструкций, модели, клиента и среды.

## Требования

- Python 3.11 или новее, Git; Python SDK и внешние зависимости не нужны.
- Для штатного адаптера: локальный Codex CLI и действующая авторизация. Аргументы сверены с `codex exec --help` версии `0.172.0-alpha.2`.
- Linux, macOS или WSL для завершения всей группы дочерних процессов по таймауту. Нативное дерево процессов Windows отдельно не проверено; используйте WSL.
- Каталог результатов вне исходного репозитория, например `/tmp/se-eval-analyze-02`. Каждый повтор получает новый каталог.

## Устройство сценария

`cases/*.json` содержит условие, источник калибровочного сценария, путь к фикстуре, команды проверяющего и скрытый rubric. `fixtures/<id>/` содержит только проект и необходимые для задачи сведения. Исходные таблицы калибровки остаются в справочниках навыков; поля `source` сохраняют связь с ними.

Минимальный контракт:

```json
{
  "schema_version": 1,
  "id": "example-01",
  "title": "Название",
  "kind": "analysis",
  "source": {"path": "path/to/calibration-scenarios.md", "scenario": 1},
  "fixture_dir": "evals/fixtures/example-01",
  "prompt": "Поручение кандидату без ожидаемого ответа.",
  "checks": [
    {"id": "contract", "argv": ["python3", "-m", "unittest"], "cwd": ".", "timeout_seconds": 10, "expected_exit": 0}
  ],
  "rubric": {
    "criteria": [{"id": "c1", "expectation": "Смысловой критерий для независимого проверяющего."}]
  },
  "limits": {"timeout_seconds": 180, "max_output_bytes": 200000}
}
```

Дополнительные поля:

- `setup`: доверенные команды подготовки. Runner сначала создаёт исходный Git-коммит, затем выполняет setup и снимает baseline. Так можно задать уже существующие staged/unstaged изменения.
- `stages`: последовательность `{id, prompt, setup?, checks?}`. Каждый этап получает отдельный запуск кандидата. `stage.setup` выполняется перед его снимком состояния; `stage.checks` — после него. `{plan}` заменяется первым ответом, `{previous_output}` — предыдущим ответом.
- `rubric.pass_conditions` и `rubric.fail_conditions`: дополнительные указания независимому проверяющему.
- `limits.total_seconds`: предел времени всех этапов и проверок одного запуска после подготовки.

Проверки выполняются через argv без shell-интерполяции. Доступные подстановки их аргументов: `{workspace}`, `{baseline_dir}`, `{stage_before_dir}`. Рабочая директория команды должна находиться внутри проекта. Команды setup/checks считаются доверенным кодом автора набора.

## Подготовить и запустить

Из корня репозитория:

```bash
python3 evals/runner.py list

python3 evals/runner.py prepare \
  --case analyze-02 \
  --output /tmp/se-eval-analyze-02

python3 evals/runner.py run \
  --run-dir /tmp/se-eval-analyze-02 \
  --adapter codex \
  --model gpt-6-luna \
  --effort high \
  --timeout 180 \
  --total-seconds 600
```

Модель задаётся явно. Это пример выбора, а не утверждение о доступности этой модели в любом аккаунте. `--codex-binary /path/to/codex` позволяет выбрать конкретный клиент. Вместо отдельной подготовки можно передать `run --case analyze-02 --output /tmp/new-run ...`.

Без независимой смысловой оценки результат сценария с rubric — `NEEDS_REVIEW`, даже когда все команды проверяющего прошли. Ни слова «тесты прошли» в ответе, ни модельный флаг `success: true` не превращаются в PASS.

Runner запускает по одному case за команду. Он не расходует бюджет на весь набор по умолчанию. Для сравнения версий повторяйте одни и те же case с одинаковыми моделями, параметрами и средой; сохраняйте каждый результат отдельно.

## Что получает кандидат

В `workspace/` копируются фикстура, текущий корневой `AGENTS.md` и текущие навыки из `.agents/skills/`. Файлы `calibration-scenarios.md` исключаются, чтобы ожидаемые ответы не попали кандидату. Ссылки на них в тексте навыков сохраняются; эти справочники намеренно недоступны в испытании. Метаданные записывают хеши именно скопированных файлов, а не заявляют тождество полного пакета.

`case.json`, rubric, команды скрытых проверок, process logs и метаданные находятся вне `workspace/`. В stdin кандидата передаётся только поручение текущего этапа. В многоэтапной задаче последующее поручение также может включать предыдущий ответ.

Адаптер Codex использует `--ephemeral`, `--ignore-user-config`, `--json`, отдельный файл последнего ответа и `workspace-write`. Он отключает hooks, apps, plugins, memories, web search и субагентов для контролируемого опыта; системные и пользовательские навыки исключает параметрами текущего запуска. Навыки испытываемого репозитория остаются в проекте. Обнаруженный глобальный AGENTS останавливает запуск, чтобы незаметно не смешивать наборы инструкций. Каталоги SQLite и логов задаются только на время запуска внутри его артефактов. HOME, CODEX_HOME, авторизация и глобальные настройки не переписываются.

Это изоляция задачи и входных данных, **не защита от враждебного кандидата на общем хосте**. Отдельная копия проекта и Git не запрещают чтение всех остальных доступных файлов. Для испытаний против умышленного поиска скрытого эталона используйте отдельный контейнер/хост с ограничениями чтения через command adapter. Отсутствующие в тестовой среде MCP-инструменты также не доказывают правильный выбор модели при наличии таких инструментов.

## Независимая смысловая оценка

Можно запустить отдельный Codex-процесс проверяющего:

```bash
python3 evals/runner.py grade \
  --run-dir /tmp/se-eval-analyze-02 \
  --judge-adapter codex \
  --judge-model gpt-6.2-sol \
  --judge-timeout 180
```

Проверяющий запускается отдельно, в пустой рабочей директории и read-only sandbox. Он получает исходное поручение, скрытый rubric, ответы кандидата, исходные и итоговые файлы фикстуры, Git diff/status и реальные результаты проверок. Содержимое кандидата явно обозначено как недоверенное свидетельство. Критерии оцениваются по смыслу; поиск ключевых слов не применяется.

Формат решения:

```json
{
  "verdict": "PASS",
  "criteria": [
    {
      "id": "c1",
      "verdict": "PASS",
      "reason": "Почему наблюдаемое поведение выполняет критерий.",
      "evidence": [{"artifact": "stages/candidate/final.txt", "quote": "Точная цитата из этого артефакта"}]
    }
  ]
}
```

Каждый criterion должен присутствовать ровно один раз. Для PASS/FAIL требуется свидетельство, существующий путь артефакта и дословная цитата из него. Runner проверяет эти свойства и согласованность общего verdict. Недостаточность доказательств обозначается `NEEDS_REVIEW`. Автоматическая проверка цитаты подтверждает наличие текста; правильность смысловой оценки остаётся ответственностью независимого проверяющего.

Если пакет свидетельств превысил бюджет, PASS автоматически понижается до `NEEDS_REVIEW`. Неуспех фактической проверки не может быть переопределён положительным ответом judge.

## Другой клиент через command adapter

```bash
python3 evals/runner.py run \
  --case analyze-02 --output /tmp/se-other-client \
  --adapter command \
  --command-json '["my-agent-wrapper", "--cwd", "{workspace}", "--output", "{output_file}"]' \
  --version-command-json '["my-agent-wrapper", "--version"]'
```

`my-agent-wrapper` — ваш существующий исполняемый адаптер; runner его не устанавливает. Поручение всегда поступает в stdin, также доступен `{prompt_file}`. Если argv содержит `{output_file}`, ответ должен появиться в этом файле; иначе ответом считается stdout. Не смешивайте служебные журналы и финальный ответ в stdout такого адаптера. Для judge действует `--judge-command-json`, дополнительно доступен `{schema_file}`. Это отдельный процесс, которому передаётся проверяющий пакет, а не контекст кандидата.

Версия generic-кандидата определяется только через `--version-command-json`; для отдельного клиента проверяющего задайте `--judge-version-command-json`. Без соответствующей команды версия остаётся неизвестной, а версия кандидата не приписывается проверяющему.

Нативный адаптер Claude в набор не входит. Через command adapter можно подключить свой wrapper без изменения runner.

## Передача задачи облачному агенту

Когда автоматический CLI недоступен, можно проверить одиночный сценарий через отдельного облачного кандидата:

1. Выполнить `prepare`. Передать кандидату только `workspace/` и `prompt`, без JSON сценария, rubric и справочников с ответами.
2. Сохранить финальный ответ и наблюдавшийся журнал инструментов. Журнал должен исходить от оркестратора; рассказ кандидата о своих действиях не является журналом исполнения.
3. Зафиксировать результат:

```bash
python3 evals/runner.py record \
  --run-dir /tmp/se-eval-analyze-02 \
  --response-file /tmp/candidate-response.txt \
  --trace-file /tmp/observed-tool-events.jsonl \
  --client-label 'ChatGPT Work, candidate thread ID' \
  --model ACTUAL_MODEL_ID
```

`record` поддерживает только одноэтапные задачи без stage.setup. Он выполняет независимые checks и собирает реальное состояние файлов/Git. Метаданные содержат `execution_mode=external_record`, происхождение внешних данных и `candidate_exit_code=null`; автоматический CLI transcript не заявляется. Сам runner не удостоверяет происхождение переданного внешнего журнала.

Если фактический журнал недоступен, `--trace-file` можно опустить. Тогда оценка опирается на ответ и независимо собранные артефакты; утверждения кандидата о выполненных командах остаются неподтверждёнными. Проверяющий не должен заменять отсутствующий журнал пересказом кандидата.

Другой облачный проверяющий получает пакет, который формирует `runner.judge_packet`, и JSON schema из `runner.judge_schema`. Его решение можно передать явно:

```bash
python3 evals/runner.py grade \
  --run-dir /tmp/se-eval-analyze-02 \
  --judgment-file /tmp/independent-judgment.json \
  --judge-label 'ChatGPT Work, independent reviewer thread ID'
```

Внешняя оценка помечается `judge_mode=external_record`. Не выдавайте такой результат за проверку Codex CLI или за автоматический прогон всей матрицы.

## Артефакты, бюджеты и статусы

В каталоге запуска сохраняются:

- `metadata.json`: версия пакета, Git-коммит источника, dirty-состояние, хеши инструкций, Python/OS/архитектура хоста, указанные клиент/модель/параметры и пределы.
- `baseline/`, `stages/<id>/before/`, `stages/<id>/after/`, `after/`: файлы, хеши, Git status, diff относительно HEAD, diff относительно baseline-коммита, staged diff, HEAD и журнал коммитов. Сравнение с baseline сохраняет также изменения, которые кандидат уже закоммитил.
- `stages/<id>/process/`: точный argv, время, exit code, ограниченные stdout JSONL и stderr. Для Codex `trace-summary.json` содержит наблюдавшиеся типы событий и reported usage; при отсутствии таких событий стоимость и токены не выдумываются.
- `checks/` и проверки этапов: реальные stdout/stderr, exit codes и результат каждой команды.
- `judgments/`: отдельные запуски/решения проверяющего. `result.json` — последняя оценка; прежние решения judge сохраняются.

По умолчанию кандидат получает 120 секунд на этап, 600 секунд на этапы и проверки после prepare; judge имеет отдельные 120 секунд. Вывод одного процесса ограничен 1 MiB, пакет judge — 512 KiB, снимок workspace — 10 MiB. Более строгие case limits имеют приоритет над CLI для кандидата. Таймаут или превышение вывода завершает процессную группу на POSIX. Это ограничения времени и объёма вывода, **не обещание жёсткого лимита API-токенов или денег**.

| Статус | Exit code | Значение |
| --- | --- | --- |
| `PASS` | 0 | Все обязательные независимые проверки и применимые смысловые критерии подтверждены. |
| `FAIL` | 1 | Независимая проверка или смысловая оценка установила нарушение критерия. |
| `ERROR` | 2 | Не удалось выполнить опыт или проверку: запуск, timeout, отсутствующий output, некорректный judge и другие ошибки инфраструктуры. |
| `NEEDS_REVIEW` | 3 | Проверки выполнены, но отсутствует независимая смысловая оценка либо недостаточно свидетельств. |
| `SKIPPED` | 4 | Подготовленный опыт явно пропущен с причиной; выполнения не было. |

Для явного пропуска до запуска: `skip --run-dir /tmp/se-eval-analyze-02 --reason 'Клиент недоступен'`. Уже выполненную ошибку нельзя скрыть этой командой.

Повторные `prepare`, `run`, `record` и `skip` для завершённого trial отклоняются с exit code 2, сохраняя его артефакты и предыдущий результат. Для нового опыта используйте новую директорию. Явный `grade` выполняет новую оценку: ошибка проверяющего сохраняется как `ERROR`, даже если прежняя оценка была PASS.

## Проверка самого runner

```bash
python3 -m unittest discover -s evals/tests -v
```

Тесты проверяют отказ при path traversal/symlinks, отсутствие эталона в workspace, границы argv и бюджета, завершение детей по таймауту, nonzero/missing output, реальные diff/check outputs, отдельный контекст judge, проверку цитат, статусы и передачу плана между этапами. Их процессы-кандидаты и judge — тестовые двойники. Их PASS подтверждает работу harness, а не прохождение 26 поведенческих сценариев моделью.
